# ADR-014: 调谐能通过 API 换（判据是组件 310 的逐件清单）；平衡调整是最低三项各 +1

- Status: accepted
- Date: 2026-09-22
- Decision By: maintainer
- Scope: `services/armor_mod_service.py`、`build/tuning.py`、`build/armor_rules.py`、`scripts/verify_tuning_write.py`

## Context

两条长期挂着的"上游限制"结论，2026-09-22 用同一支真机脚本
（`scripts/verify_tuning_write.py`，做法照 `verify_armor_mod_sockets.py`：读现状 → 换一颗 →
回读插槽与组件 304 的六维 → 换回原样）一次问清楚了。

**一、调谐到底能不能写。** 以前有两代说法，都不对：

- 「Bungie 只允许游戏内改（实测 `This action can only be done in-game.`，1663）」——
  那个 1663 是 ADR-012 查出的**字段名 bug**（`itemId` 缺失），不是"调谐不可写"的证据；
- 「本项目还没验证过」——诚实，但一直占着位置，用户问"能不能帮我改"时只能回答不知道。

真机结果分两种，取决于**你有没有那颗调谐**：

| 目标 | 结果 |
| --- | --- |
| 换成身上**别的护甲正装着**的那颗（`平衡调整` 3122197216） | `ErrorCode=1`；回读插槽 = 目标 hash；组件 304 的六维按下面的规则变；换回原样也成功 |
| 换成一颗**你没有**的（`+手雷 / -生命值` 455024236） | **1675** `DestinyCannotAffordMaterialRequirements`（"You cannot afford the material requirements for that action."），**账号一个字节没变**（回读确认） |

两条边角事实：① 角色的"可插入清单"（`characterPlugSets`，组件 207）**根本不覆盖调谐槽**
—— 5 件护甲上**正装着**的调谐也一颗都不在里面，所以那份清单不能用来判"这个调谐能不能换"；
② 免费接口能寻址这个槽（原样重插回 1679 `DestinySocketAlreadyHasPlug`，不是报错）。

**二、平衡调整的真实效果。** Manifest 的 `investmentStats` 把 `平衡调整` 写成"六维各 +1"，
`build/tuning.py` 以前就照这个建模；`build/armor_rules.py` 的模板模型却写的是"给最低的三项各 +1"。
真机对账站后者：光芒领主面具未调谐基值 武器30/生命5/职业5/手雷30/超能25/近战5，装上平衡调整后
是 武器30/生命6/职业6/手雷30/超能25/近战6 —— **只有最低的三项各 +1，30 的那三项一动不动**。
同一个 plug 两套模型打架，求解器搜索用的偏偏是错的那份。

**What changed**：这一条是**新增结论**（不是推翻我们自己的设计）：调谐写入从"未知/不可写"
变成"可写，条件明确"；平衡调整的模型从"六维 +1"改成"最低三项 +1"。

## Decision

1. **调谐写入的唯一判据是"这颗在不在**这件护甲**允许的那几颗里"** —— 权威出处是组件 310
   `ItemReusablePlugs`（每件给 5 颗"某一个属性 +5"的定向调谐 + 平衡调整；**金装是全部 31 颗**）。
   不是角色的可插入清单（`characterPlugSets` 里调谐槽只有"空"这一颗、角色级干脆没有），
   也不是"你有没有这颗"——
   **2026-09-22 追加纠正**：本条原文写的是"只能换成你已经拥有的那一颗"，那是从一次实验
   （把头盔换成身上另一件正装着的平衡调整，成功）推出来的**近似**。真规则是"**这件允许的**"：
   那次能成，是因为**平衡调整本来就在那件头盔的清单里**。随后用户指出"每件的调谐对象不一样"
   （两件同名手套分别只能加职业/近战），读组件 310 得到证实。1675
   `DestinyCannotAffordMaterialRequirements` 因此读作"**这颗装不到这件上**（不在清单里）"，
   而不是"你没拥有它"。
2. **1675 的措辞固定为"这颗装不到这件上（不在这件护甲允许的清单里）"**，不许说成
   "上游不允许 API 改"、不许说成"你没有这颗"、也不许说成"稍后重试"。1679 是"槽里已经是这颗"，
   **不是失败**。（本条 2026-09-22 二次修正：原文写"要材料 / 你没有这颗"，真因是 310 清单。）
3. ~~**本项目暂不替用户写调谐**~~ —— **2026-09-22 作废**，见下面的修订：写入已开放为正式能力，
   `canonical_build` 现在**带着**调谐插件（只带这件允许的）。
4. **平衡调整的单一出处是 `armor_rules.balanced_tuning_bonus`**：恰好三项并列最低时给那三项 +1，
   否则一项都不加（"不适用"必须返回**等长的全 0**，不能返回空元组 —— 返回空元组会让
   `delta[index]` 直接 IndexError，第一版就这么写的）。`build/tuning.py` 的目录里那份 `delta`
   是**全 0 占位**，真实增量由 `PieceTuning.choice_delta` 按这件的基础六维现算；
   `TuningChoice.is_noop` 只认"空插槽"，不许用 `not any(delta)` 判（会把平衡调整当成空操作）。
5. **反推未调谐基值时，平衡调整要解不动点**：猜哪三项拿了 +1、减掉、再正着算一遍，
   能还原观测值才认；猜不出来就整件"保持现状"+ 一句话说明，**不许编一个基础值**。

## 修订（2026-09-22 同日）：写入已开放为正式能力

原本"本项目暂不替用户写调谐"（决定 3）已作废：真机证明写入**不花材料**（清单内的调谐
`ErrorCode=1`，四件护甲的调谐都这么写成功），于是按 `docs/plans/TUNING_WRITE_PLAN.md` 做成了
正式路径 —— `equip_build` / `equip_mod` 会在用户 `confirmed=true` 之后连同护甲与模组一起写调谐。
判据仍是上面那条（组件 310 的清单），执行端走的就是护甲模组那条路（`mods` → 按类别找槽）。
**仍然不做**：写清单外的调谐（1675 如实报）、自动回退、替用户判断"值不值"。

**同日追加修订（判据只剩一条）**：`unlock_state`（组件 305 / 角色级 plug set 的"这一位能不能插"）
对调谐**不可信**，已从调谐判据里删掉 —— 真机实测：调谐槽里正装着的那颗都不在清单里，而一颗被判
`false` 的调谐写入**照样成功**（`ErrorCode=1`，回读核对）。原来那个 `and unlock_state is not False`
会把能装的调谐报成"游戏里同样装不上"。现在调谐只看 310 清单，且 `unlock_state` 对调谐一律报
`null`（不把一个已知错误的值当判据发出去）。

## Consequences

- 求解器对平衡调整的估值回归真实：以前"六维各 +1"会**每项多算 1**（总账最多虚高 6 点），
  而且换成方向型调谐时基础值会反推错。修完的实测差异见 `docs/plans/SOLVER_OPTIMALITY_PLAN.md`
  的 P4/P5 记录。
- "只能换成你已经拥有的那颗"带来一个**新的产品约束**：调谐建议必须落在用户已有的调谐上，
  否则给的就是一条他做不到的方案。当前实现（`plan_tuning`）还没有这一步筛选 ——
  列在计划文档的待办里，**不许**在没做这一步之前承诺"照这个改就能达标"。
- 真机验证脚本进仓（`scripts/verify_tuning_write.py`），含 `--apply` 才写入、`--to` 指定目标、
  `--include-empty` 试"撤掉调谐"。以后再有"调谐到底行不行"的问题，跑它，不要重开一轮猜测。
- 调谐写入这条能力要真正开放，得先回答"能不能替你花材料"；在那之前所有话术都是"给清单"。
