# 计划：突袭/地牢战绩报表（raid.report 那种表）

状态：**P0 已完成**（2026-09-30 真机实测，结论见 `docs/reference/bungie_api.md` 第十六节）。P1 待你点头开工。

缘起：两张截图（`OneTop丶Husky#6641` 的突袭页与地牢页）。
第一次规划里我把「导师次数」和「排名」判成"算不了"，**真机实测推翻了其中一条**：
导师列就是官方计数器，而且整张表的数字几乎全部能在组件 1100 里逐字对上。下面是修订后的版本。

---

## 一、最重要的结论（这一版和上一版最大的差别）

> **这张图的本质，是把游戏内的官方计数器排了个版。**

真机对照（2026-09-30，只读组件 1100）：

| 副本 | 官方 `X 完成数` 计数器 | 截图「完成次数」（普通+大师） |
| --- | --- | --- |
| 深岩墓室 | **229** | **229** |
| 救赎花园 | **140** | **140** |
| 异端深渊 | **117** | **117** |
| 预言 | **91** | **91** |
| 国王的陨落 | **103** | 101 + 2 = **103** |
| 梦魇根源 | **96** | 93 + 3 = **96** |
| 战争领主的废墟 | **39** | 38 + 1 = **39** |
| 守望者尖塔 | **36** | 31 + 5 = **36** |
| 晚星之主 | **28** | 27 + 1 = **28** |
| 忧愁王冠 / 星之塔 / 最后一愿 / 永恒沙漠 / 往日之苦 | 26 / 6 / 81 / 2 / 48 | 全部逐字吻合 |
| 玻璃拱顶 | **53**（导师列） | 51 + 2 = **53** |

**15 个副本的「完成次数」与官方计数器逐字相同，不是估算、不是接近。**
导师列同样吻合（深岩墓室 56、星之塔 11、克洛塔的末日 21、梦魇根源 33、忧愁王冠 11、往日之苦 22、永恒沙漠 2、分离教义 0 全部对上；
另有 7 个差 1~11，是**截图那一刻与当前计数器的时差**，不影响结论）。

**两个直接后果：**

1. **核心三列不用扫 PGCR。** 上一版估的「2,000~4,000 场、2,000 次调用、5~15 分钟冷扫」**不成立** ——
   完成数与导师列全在一次 `GetProfile(components=[1100])` 里。这让功能从"大工程"变成"中等工程"。
2. **「按副本为单位、大师/巅峰含在其中」被数据验证是对的。** 玻璃拱顶 `51+2=53` 正好等于官方那一个数，
   说明官方计数器本来就是**按副本**计的，拆成两行反而要我们自己相加。

**一个被推翻的假设**（全量实测，2026-09-30 追加）：一度以为"逐场 PGCR 能把这张表整个复刻出来"。
**不行。** `GetActivityHistory` 本身漏场次（救赎花园历史 133 场 < 官方 140 次完成），
所以**「全程次数」复刻不了**（我们算 38，截图 110），**站点那套徽章也复刻不了**。
最终形态：**三列可复刻**（完成数、导师、最短用时），其余按官方口径或不做。详见
`docs/reference/bungie_api.md` 16.6 / 16.7。

## 二、四列指标的数据来源（逐列落定）

### 列 1「完成次数」——✅ 官方计数器

`X 完成数`（all-time）。真机对照 15/15 逐字吻合。判据：描述里**不含**「本周 / 本赛季 / 本篇章」。

### 列 2「担任导师次数」——✅ 官方计数器（**上一版判错了**）

`X 导师`，描述形如「带领完成首次"深岩墓室"突袭的守护者**总人数**。自第12赛季开始计算。」

- **单位是"人数"不是"次数"** —— 一次带 3 个新人就是 +3。这解释了图里那个怪数：
  星之塔 `全程 0 / 完成 6 / 导师 11`（官方计数器实测就是 11）。
- **同一副本有多个同名计数器**（`本周` / `本赛季` / `总人数`），**名字相同、只能靠 description 区分** ——
  这是实现时最容易踩的坑，必须写进守门测试。
- **覆盖不全**：副本级 all-time 导师计数器我搜到 19 个；图里另有几个副本（战争领主的废墟、深渊机灵、
  守望者尖塔、二象性、贪婪之握、预言、异端深渊、破碎王座……）**没有** all-time 导师计数器。
  这些行要么留空、要么去找它们的赛季变体 —— 按 `coverage_complete` 的口径如实标注，不许填 0。

### 列 3「全程最短用时」——✅ PGCR 可精确复现（P0 已定标）

**不用 `时间试炼` 计数器**（实测：与真实最快时间的比值在不同副本间从 40 到 979，不存在一致的单位）。

正确来源是逐场 PGCR，判据（实测对着一张 raid.report 截图逐项核对）：

```
用时 = activityDurationSeconds
条件 = activityWasStartedFromBeginning == true（实例级）且 本人 completed == 1
```

- 救赎花园：`1843.0s` = **30m43s**，与截图**逐秒吻合**；
- 分离教义：`4807s` ≈ 截图 `1h20m`（截图只到分钟）。

两个坑：**`activityDurationSeconds` 是实例时长不是本人时长**（`startSeconds`/`timePlayedSeconds` 才是玩家级，
实测一场救赎花园实例 6161s、本人只打了 599s）；**不要加玩家级过滤**（加了会把合格场次砍掉、最小值反而变大）。
细节见 `docs/reference/bungie_api.md` 16.1。

### 列 4「全程次数」——⚠️ **能算，但要先选口径**（根因已查明，不是数据拿不到）

判据本身是明确的（PGCR：`activityWasStartedFromBeginning == true` 且本人 `completed == 1`），
用户给的定义也与此一致（**全程 = 从第一关打到最后一关；完成 = 结算算通关，含中途加入、跳关、拿存档点**）。

**但全量实测证明这一列做不准**：把三个角色的历史翻到底（17,155 场）逐场取 PGCR 之后——

| 副本 | 我们算的「全程」 | 截图「全程」 |
| --- | --- | --- |
| 深岩墓室 | 38 | **110** |
| 救赎花园 | 50 | **120** |
| 破碎王座 | 16 | 25 |

差三倍的根因**不在数据源，在字段本身**：`activityWasStartedFromBeginning` 历史上坏过三段
（Bungie 官方 issue #1601，员工确认，工单 TFS 1070650）：

| 时期 | 状态 | 我们的处理 |
| --- | --- | --- |
| Beyond Light 之前 | `startingPhaseIndex` 有效 | 用它判 |
| Beyond Light → 巫后（2020-11 → 2022-02） | 两个字段都坏，Bungie 原话「**永远修不了**」 | **只能按口径约定** |
| 2022-02-21 起 | 有了布尔值，但 2022-03-10 查出**团灭过就永久变 False** | 仍不可靠 |
| **2022-05-24 修复** | 团灭不再影响；**修复不追溯** | 这一天之后才可信 |
| 最后一愿 | **游戏 bug 至今没修**：只有 5% 的 PGCR 报 fresh（其他突袭 ~90%） | 这一行单独标不可靠 |

**两家大站对"坏窗口"的处理相反**（RaidHub FAQ 原文）：RaidHub 默认算**存档点**，raid.report 默认算**全程**。
我们的截图来自 raid.report，所以它偏高——**不是谁算错了，是口径选择不同**。

**结论：这一列做，但要显式声明口径**（建议与截图一致 = raid.report 那套，这样和用户看到的东西对得上），
响应里带 `policy` 字段；最后一愿标注不可靠。**要说"口径未定"，不能说"数据拿不到"——后者是错的。**

> 另一处仍未解释的账：救赎花园历史里只有 **133 场**，官方计数器写 **140 次完成**。
> 最可能的原因是**已删角色**——本项目早就实测过"统计接口的 `mergedAllCharacters` 已含已删角色"，
> 而已删角色的活动历史在 API 里查不到。这一条待定，不影响上面的结论（全程按 PGCR 算，与总场次无关）。

### 徽章（8 种）——⚠️ 站点的定义复刻不出来，改用官方计数器 + 自家命名

**官方计数器能给的**：`Flawless`（= `X 无瑕完成数`）、`Flawless Solo`（= `X 单人无瑕完成数`）。
**官方没有的**：`Duo` / `Trio`（只能从 PGCR 的 `playerCount` 推，且它**不等于队伍人数**——
实测 6 人突袭里出现 `playerCount = 7 / 8`，中途换人算进去了）。

**但不能照截图的徽章名贴官方数字**，四个反例（`docs/reference/bungie_api.md` 16.7）：

| 副本 | 官方无瑕 | 官方单人无瑕 | 截图 |
| --- | --- | --- | --- |
| 贪婪之握 | 1 | 1 | `Flawless Solo` `Solo` **`Flawless x11`** |
| 异端深渊 | 29 | **0** | **`Flawless Solo`（有）** `Flawless x6` |
| 破碎王座 | 27 | 无此计数器 | **`Flawless Solo`（有）** `Solo x4`，**没有** `Flawless xN` |
| 二象性 / 守望者尖塔 | 1 / 1 | 1 / 1 | 这两个反而**对得上** |

而且全量数据证明**我们自己也算不出站点那套**：破碎王座按「本人 0 死」算 26 场、
按「全队 0 死」算 19 场，**截图一个 `Flawless` 徽章都没有**；`Solo` 我们算 3、截图 `Solo x4`。

**决定**：徽章用**官方计数器**，字段名用我们自己的（`flawless` / `solo_flawless`），
并在响应里标 `source: "profile.metrics(1100)"`；站点的徽章名不出现。
`DayOne` 用官方记录（有就标，没有就不标），编号不做。

### DayOne——官方有，但不是图里那个编号

组件 900 里确实有官方「首日 / 竞赛模式」记录（实测搜到 8 条）：

| 副本 | 记录 | 描述 |
| --- | --- | --- |
| 玻璃拱顶 | 顶尖速度 | 在"玻璃拱顶"突袭开放后 24 小时内完成它以及所有遭遇战挑战 |
| 国王的陨落 | 弑君者 | 在"国王的陨落"开放后 24 小时内完成突袭和所有遭遇战挑战 |
| 深岩墓室 | 初出墓室 | 在"深岩墓室"突袭发布后 24 小时内将其完成 |
| 忧愁王冠 | 首位王冠持有者 | 在"忧愁王冠"突袭发布后 24 小时内将其完成 |
| 门徒誓约 | 金字塔之日 | 在"门徒誓约"突袭发布后 24 小时内将其完成 |
| 分离教义 / 晚星之主 / 地牢"平衡" | 分而未离 / 轨道大赛 / 开荒先锋 | 以竞赛（难度/模式）完成 |

这个账号实测：`深岩墓室·初出墓室` 有记录（state=28，4 个 objective 里第一个 1/1），
`忧愁王冠·首位王冠持有者` 有记录（state=6）；其余 6 条**在档案里不存在**（说明这个账号没拿到）。

而截图里的 `DayOne #15358`（晚星之主）、`#4909`（克洛塔的末日）、`#20574`（梦魇根源）、`#7879`（国王的陨落）：

- **晚星之主、国王的陨落**的官方首日记录在这个账号里**不存在**（键都没有），截图却标了 DayOne；
- **克洛塔的末日、梦魇根源**在 Manifest 里**没有对应的 24 小时记录**；
- 记录里的 objectives 是**遭遇战进度**（`1/1, 0/1, 0/1, 0/1`），**没有任何排名信息**。

**结论**：官方给的是"你有没有在首日窗口完成"（而且不是每个副本都有），
**`#编号` 官方没有** —— 那是那个网站按全球完成顺序排的。
我们的做法：徽章用官方记录（有就标，没有就不标），**编号砍掉**；要编号只能用我们自己的口径并改名。

## 三、副本归组：需要一张自维护表（+ 守门）

用户已定：**按副本为单位，大师/巅峰含在其中**。这消掉了上一版"难度怎么归属"那个未知，但带出一个新问题：
**怎么把活动 hash 归到"副本"**。

Manifest 里的现成判据（实测）：

- `DestinyActivityDefinition.activityTypeHash`：**`2043403989` = 突袭**，**`608898761` = 地牢** —— 这是分类的第一把尺子；
- 活动名带难度后缀：`: 普通` `: 标准` `: 大师` `: 传说` `: 巅峰` `: 竞赛` `: 专家` `: 最后通牒` `: 探索者` `（史诗）` `: 等级58`；
- **不能只用名字前缀归组**：`利维坦，星之塔` / `世界吞噬者，利维坦` / `利维坦` 三条都含"利维坦"，
  但报表里是**三行**（图里就是分开的）。

所以归组要一张**人工核对过的映射表** `副本 → [活动 hash...]`，照 `data/rotations.py` 那套写
（表 + 说明 + 更新时间），并配一条守门测试：**表里每个 hash 必须真实存在、`activityTypeHash` 必须是对的那一种、
name 必须与副本名匹配**。这样 Manifest 一改，测试就红，而不是静默少一行。

## 四、接口与响应（沿用既有契约）

不新增第 9 个工具（ADR-008），是 `activity_assistant` 的新 intent：

```
activity_assistant(intent="raid_report", mode="raid"|"dungeon")
```

```json
{
  "ok": true,
  "summary": "突袭 16 个副本；数据来自游戏内计数器（组件 1100）",
  "data": {
    "report": {
      "kind": "raid",
      "rows": [{
        "activity": "深岩墓室",
        "completions": 229,
        "sherpas": 56,
        "fastest_seconds": null,
        "badges": [{"kind": "flawless", "count": 12}, {"kind": "day_one"}]
      }],
      "sources": {"counters": "profile.metrics(1100)", "notes": "…"}
    },
    "unavailable": [
      {"field": "fastest_seconds", "reason": "「时间试炼」计数器的单位与口径未实测（P0 待办）"},
      {"field": "full_clears", "reason": "官方没有「全程」口径，需要逐场 PGCR 判定"},
      {"field": "badges.day_one_index", "reason": "官方只给「是否首日完成」，不给排名编号"}
    ]
  }
}
```

三条设计要点：

1. **`unavailable` 是必填项**：哪一列给不了、为什么，写在数据里 —— 对应「不许静默降级」。
2. **`coverage`**：哪些副本没有对应的官方计数器，要列出来（19 个副本有导师计数器，剩下的没有）。
3. **`fastest_seconds` 缺就给 `null`**：截图里那些 `0m 0s` 是反面教材，界面上应该显示 `—`。

| **P2 归组表** | `data/raids.py`：突袭/地牢 × 副本 → 活动 hash；守门：hash 存在 + 类型正确 + 名字匹配 | **已完成 2026-09-30**：26 个副本共 79 个标准档活动 hash。两条踩坑都写进注释了 —— ①Bungie 的逗号命名**方向不一致**（`世界吞噬者，利维坦` 本名在前、`利维坦，星之塔` 本名在后），判据是"哪个部分不会独自作为活动名出现"；②`永恒沙漠（史诗）: 标准` 这种写法字面结尾是「标准」但其实是史诗档，得**先剥标准档标记再判难度**。守门测试拿 Manifest 现算比对，新副本/新写法会判红而不是静默归错 |

## 七、三条不能破的线

1. **缺值给 `null`，不编 `0`。** 截图里那些 `0m 0s` 是反面教材：没有全程记录就显示 `—`。
2. **来源要写在数据里。** 这一版全部数字来自 `profile.metrics(1100)`，不是我们算的 ——
   响应里要标出来，将来换成 PGCR 计算也要标出来。同一个数字换来源，就是换口径。
3. **没有官方来源的就不装。** 排名、`DayOne #编号`、没有计数器的副本的导师列 —— 不做或留空，
   不许用近似值挂真名。
