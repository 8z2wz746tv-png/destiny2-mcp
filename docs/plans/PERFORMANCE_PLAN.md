# 性能优化计划（六项已落地 + 第七项待办：装备流程）

**状态（2026-09-23）**：第一、二、三、四、六项已落地，逐项实测结果写在 `CHANGELOG.md`；
"顺带"的缓存做了两块（见下）；**第五项实测后作废**（前提是错的，见文末）；
**第七项（装备流程的往返次数）2026-09-23 记录，其中"护甲模组全表扫"那半已落地（`3a371d5`），
剩下的 A/B/C/D 四步待办**。

目标是**把"我等你回答"的时间压下来**。压不动的地方我先说清楚：Bungie 那边一次请求就要 **1.1–4.6 秒**（实测），
这是地板，改不了。但下面这六项是我们自己造成的浪费，加起来能省掉**几十秒到两分钟**。

先给改之前的基线（2026-09-19 本机实测，同一进程热身后，不是估算）：

| 场景 | 现在多慢 | 花在哪 |
| --- | --- | --- |
| 模糊搜人（`我名字记不全，帮我找找…`） | **22.6 秒** | 96% 是在给前 10 个候选逐个拉别人档案，只为算"置信度" |
| 武器目录筛 perk（`全游戏哪些手炮能出爆破专家`） | **120–135 秒** | 把全库 2208 把枪的完整明细全造一遍，再筛选，最后只返回一页 |
| 武器类型列表（`我手炮都有哪些`） | **5.6 秒 / 184 KB**（默认 20 件，单件 9.4 KB） | 每件都造插槽池 + 可换项（`sockets`+`options` 占该响应 **2/3**） |
| 最近活动（`我最近打了什么`） | 3.5 秒 | 3 个角色**逐个**拉，其实可以一起拉 |
| 生涯统计（`我熔炉生涯击败多少`） | 4.9 秒 | 统计接口和游戏内计数器**一前一后**各打一次 |
| 服务器启动 | 5.7 秒 | 游戏资料库 2.2s + 愿单与 perk 索引 2.5s（每个进程一次） |

一句话总结：**慢的不是"算"，是"多打了几次网络"和"给了太多用不上的数据"。**

---

## 第一项：搜人别再一个一个拉档案

**现在为什么慢**：你只说"找找名字带 husky 的"，我们却给前 10 个候选每人拉一次完整账号档案，
就为了排个"置信度"顺序。实测整次 22.6 秒，其中 **21.8 秒**全在这 10 次串行网络请求上，返回的数据只有 1.9 KB。

**怎么改**：
1. 10 个人**一起拉**（并发 5，两批就完），而不是排队；
2. 更推荐的做法：**默认不算分**，直接按名字给你候选清单（名字、ID、平台），
   只有你追问"这几个里哪个是他"时，才去补游玩时长和凯旋分。

**改完什么样**：22.6 秒 → **1.5 秒左右**（不算分）或 **5 秒左右**（并发算分）。

**怎么验**：真机跑一次搜人，断言"没有循环里的逐个拉取"（并发后网络调用次数不变、但墙钟时间降到 1/4 以下）；
另外保证返回字段一个不少（名字/ID/平台/候选数/page/has_more 全在）。

**不动的东西**：查别人档案的能力保留（追问时还用它），只是不再默认花 21 秒。

---

## 第二项：武器目录别"先全造好再筛"

**现在为什么慢**：你要"能出某个 perk 的手炮"，我们的顺序是**反的** ——
先把全库 2208 把枪的插槽、每个可选 perk、每条 perk 说明全查出来拼好（内部实测调了 12 万次查询），
再过滤，最后只返回一页。`type` 那条也没好到哪去：返回 5 件，却造了整库。

**怎么改**（分两步，先筛后展开）：
1. **筛的时候只用轻量信息**（武器名、类型、能不能滚出某个 perk —— 这些在索引里就有，不用展开 perk 文本）；
2. 命中之后，**只为要返回的那一页**（默认 20 件，`limit` 可调）构造完整明细。

**改完什么样**：`catalog` 120 秒+ → **个位数秒**；`type` 5.8 秒 → **1 秒内**；内部查询次数从 12 万降到几百。

**怎么验**（这条最怕改错内容）：改完必须做到"**内容零变化**"——
用现成的武器语料（17 行）跑一遍，再和改前的响应基线逐字段比对；一旦有字段差异就是错的，不是"优化"。

**风险**：中等。它动的是"筛选与载荷构造的顺序"，逻辑本身不变；
风险点在"漏了某个字段"或"筛选条件和原来不等价"，靠基线 diff 挡住。

---

## 第三项：三个角色别排队，一起查

**现在为什么慢**：账号下的历史战绩是**按角色**存的，我们有 3 个角色就串成 3 次网络请求（每次 1–4 秒）。
"最近打了什么"实测 3.5 秒，"纯 PvP 武器榜"里拉历史那 3 次也一样是排队。

**怎么改**：3 个角色的历史改成**一起拉**（并发），拿到后按时间合并。
武器榜里"逐场拉结算"那部分**保持现状**（实测并发 3 最快，加到 6 反而更慢）。

**改完什么样**：`history` 3.5 秒 → **1.5 秒左右**；武器榜每次省 2–4 秒。

**怎么验**：真机 history 断言"条数、排序、字段与改前一致"，只允许耗时变短。

**不动的东西**：**账号写入**那些循环（换装备、装模组、回滚）**绝对不能并发** ——
它们有先后顺序，一件失败还要按顺序回滚，并发会把回滚搞乱。这条写死在计划里。

## 第四项：列表视图别再塞明细（这项对"回答快慢"影响最大）

**现在为什么慢**：不是服务器慢，是**模型要先读完一大坨才能开口**。
`我手炮都有哪些` 默认 20 件返回 **184 KB**（单件 9.4 KB，其中 2/3 是插槽池与可换项）；
重复武器 **85 KB**；配装列表 **71 KB**；连"我熔炉生涯击败多少"那种问题也要读 60 行 ≈ **30 KB**。
（口径：解码后的紧凑 JSON 字符数，与 `docs/testing/TESTING_CORPUS_FULL.md` 的"最大响应"表一致；
线上文本带 `\uXXXX` 转义，同一份响应约是它的 2 倍。）

按 4 个字符≈1 个 token 粗算，**184 KB ≈ 4.6 万 token** —— 每次调用模型都要 prefill 这么多，慢就慢在这。
一个反直觉的实测：这么大一坨里，**字符串只占 18 KB**，真正占地方的是**结构本身**（成千上万个小字段）。
所以"删掉图标链接"没有用，**要少给整块内容**。

**怎么改**：
1. 列表/概览类回答**只给列表该有的字段**（名字、类型、稀有度、关键数值、实例 ID、位置），
   插槽与 perk 明细改成"你要看某一件时再查"；
2. 生涯统计支持"我只要某几项"（比如只说"击败对手"就只回那几行）；
3. 默认条数下调（现在"手炮列表"默认 20 件 ≈ 700 KB，改成默认 10 件 + 明确告诉你还能翻页）。

**改完什么样**：一次调用从几万 token 降到几千；`type` 从 184 KB → **20–40 KB**。

**落地结果（2026-09-20 实跑，同一账号）**：`type` 改成**列表行**（身份摊平 + 位置/光等 + `stats`，
不带 `sockets`/`options`），默认 20 → **10 件**，并补上 `offset`/`next_offset` 翻页。
默认调用 **184 KB → 23.2 KB**（同样 20 件是 44.7 KB，单件 9.4 KB → 2.3 KB）；
线上文本 387,598 → 41,537 字符（9.3×）。顺带两处：列表视图**不再请求 305/310**
（profile 10.16 MB → 1.86 MB，实测 3.79s → 0.63s），也不再逐把读本地资料
（整张列表的清单仍在顶层 `farming_list`）。形状变更与旧→新对照见 `docs/COMPATIBILITY.md`。

**怎么验**：响应体积基线（仓库里已有"最大响应"记录）逐项下调；同时用真机确认"信息没丢"——
丢的是嵌套明细，不是你要的答案；需要明细时一次调用就能拿到。

**风险**：这条是**改对外形状**，属于破坏性变更，按仓库规矩要：升小版本 + CHANGELOG 写清 + 基线同步重录。

## 第五项：启动那 5.7 秒（影响最小，但顺手能省）

**现在为什么慢**：每次进程起来要 ① 打开游戏资料库并建索引 **2.2 秒**；② 加载愿单 1022 把枪 + 12245 条 PvE perk + 10106 条 PvP perk **2.5 秒**。

**怎么改**：资料库保留同步（所有查询都靠它）；**愿单与 perk 索引改成后台加载**——
先能回答问题，愿单相关的功能（god roll 评分）在它准备好之前给一句"还在加载"。

**改完什么样**：启动 5.7 秒 → **2 秒出头**。

**说实话**：常驻的 MCP 服务器**只在会话第一次付这个钱**，所以这条对"每次回答的速度"几乎没影响，
优先级放最后（除非你经常重启服务）。

**实测后作废（2026-09-20）：这一项的前提是错的，决定不做（先不动）。**

| 启动里的一段 | 计划里写的 | 实测（本机，同一台） |
| --- | --- | --- |
| `bungie.start()`（客户端） | — | 0.00s |
| Manifest 打开 + 建索引 | 2.2s | **2.83–3.77s** |
| 愿单 + perk 索引加载 | 2.5s | **0.31s**（25 MB JSON / 1022 把枪 / 12245 + 10106 条 perk） |
| 客户端握手到能应答（合计） | 5.7s | 2.99–3.55s |

按原方案把愿单挪到后台**只能省 0.31s（约 10%）**，还要额外引入"愿单还在加载"这种一不留神
就会把"没收录"说成结论的状态 —— 花这个复杂度不值。真正吃时间的是 **Manifest 建索引**：
`_build_name_index` 对**两个语言**的库各做一次 `SELECT id, json`，每行 `json.loads` 整个物品定义，
而实际只用到 9 个字段。要动它得先在 `manifest_*.py` 上出方案（SQL 侧 `json_extract` 只取需要的字段，
或把索引按 Manifest 指纹落盘复用），属于动核心模块，**另开一页计划再动手**。

## 第六项：两个来源并行去拿（统计接口 + 游戏内计数器）

**现在为什么慢**：`我熔炉生涯击败多少` 要同时给"统计接口的 78,864"和"游戏内的 124,495"，
这两个来源是**一前一后**去拿的（各 1–2.5 秒），实测总 4.9 秒。

**怎么改**：**同时去拿**（并发），谁先回来先放着；计数器拿不到照样只降级（不影响统计结果）。

**改完什么样**：4.9 秒 → **3 秒左右**。

**怎么验**：断言两个来源的数字与改前完全一致（78,864 / 124,495），只允许耗时变短；
计数器失败时仍然给 `counters_unavailable` 的说明，不静默。

## 顺带一项：缓存（不单列，但它服务上面好几项）

现在有缓存的是：PGCR 结算（不可变，永久）、你自己的档案（有 TTL 和后台刷新）、游戏资料库（内存）。

**缺的三块**：
1. **别人的档案摘要**（第一项每次重拉同一批人）→ 加几分钟 TTL，重复搜同一前缀几乎瞬时；
2. **目录筛选结果**（第二项同一条件重复问要再等 120 秒）→ 按"筛选条件指纹"缓存结果；
3. **历史/结算窗口**（武器榜换个场次数就全重拉）→ 结算已有缓存，历史那 3 次靠第三项的并发就够。

**落地结果（2026-09-20）**：① 做了 —— 候选档案 5 分钟 TTL（只缓存成功结果）；
③ 按计划不做（第三项的并发已经够）。
② **换了做法**：真正贵的是 `list_weapon_catalog` 那一次全量索引遍历（真机 **1.06s**），
所以缓存在**那一层**按 (类型, 名字) 记忆化（`limit` 在读取时切、Manifest 重载时清空）——
`catalog` 与 `type` 同时受益（实测 `type` 热调用 0.70s → **0.31s**），
而且不必缓存账号侧结果，避开了"哪些枪能出某个 perk"因物品移动而过期的风险。

## 第七项：装备流程别抓 5-6 次 profile（待办）

**已落地的那半（2026-09-23，`3a371d5`）**：护甲模组的"全表扫"
（`SELECT id,json FROM DestinyInventoryItemDefinition WHERE json LIKE '%"itemType":19%'`
→ 一万多行逐行 `json.loads`）以前**每次护甲快照都重扫一遍**；cProfile 实测它占一次快照 7.3 秒里的
**5.8 秒**。改成按 `(部位, 类别)` 记忆化（失效走 `_load_from_file` 那张派生缓存清单，出参发浅拷贝）后，
真机**快照 10.9 秒 → 3.2 秒**（冷启第一次仍要扫一次；宿主是长驻进程，之后整场会话都吃这份缓存）。
`find`/`recommend`/`analyze`/`farm_target`/`equip_build` 都吃这个。

**还没做的那半（一次 `equip_build` 的网络往返）**：

| 事实 | 实测（2026-09-22/23 本机） |
| --- | --- |
| 一次 profile 抓取 | **2.9 秒**（3.3 MB；带组件 310 的 8.9 MB 也一样 —— 载荷不是问题，网也不慢） |
| 一次 `equip_build` 抓几次 | **4 处明确 + 一处最多 8 次的轮询**：`_equip_local_unlocked`（规划用）、`_verify_loadout`（回读）、批量装备前的 `read_until`（等同步窗口）、`_fetch_all_items`（recovery 与搬运核对） |
| 批量装备 | **已经在用**（`EquipItems`，一次调用）—— 不用再找"批量接口"，它**不是**瓶颈 |
| 单颗模组写入 | 免费插槽接口 ~1–3 秒；搬运"已经在目标角色身上"的会直接跳过 |
| 审计里那次 80.9 秒的 `equip_build`（9/21） | 是**旧的付费路径**：5 颗模组全被 403 `AdvancedWriteActions` 拒 → 失败+回退重试的开销，**不是正常耗时**，别拿它当基线 |

**四步（按性价比排序）**：

| 选项 | 做什么 | 省 | 风险 |
| --- | --- | --- | --- |
| A | 一次装备只抓 1–2 次 profile：写前那一份复用给规划与搬运核对，只保留一份"写后回读" | ~9–12 秒 | 低 |
| D | `find` → `equip_build` 复用同一份快照（按已有的 `snapshot_version` 校验，不新增口径） | ~3 秒 | 低中 |
| B | 5 件护甲的搬运**有界并发**（3 路；跨角色仍是 vault 两跳 + 每跳 0.75 秒） | ~5–10 秒 | 中（上游写并发，要真机验） |
| C | 不同护甲之间的模组写入并发（**同一件内**"先清能量再写"必须保序） | ~2–4 秒 | 中 |

顺序 **A → D → B → C**。**实测口径**：`~/.destiny_mcp/audit/*.json` 每次调用都记 `duration_ms`
（**包含用户在 GUI 里的调用**，不是自测脚本），拿它做前后对比；每步收尾再跑一次**幂等装备**
（装当前这套、不改任何东西）—— 那一次会写账号，**必须先得到用户确认**。

**不做**：为了省往返删掉"写后回读"（同步窗口 3–10 秒是实测的，删了就是把成功报成失败）；
不加保序地并发账号写入。

## 第七项补记（2026-09-23）：一次装备 5 分钟 → 65 秒，根因是三处 1679 与一处预检

上面那张表里"审计里那次 80.9 秒不是基线"这句话**当天就被推翻了**：为第七项记基线，我写了
`scripts/benchmark_equip_chain.py`（只读半分随时可跑，`--write` 真写一次并分段计时），第一次真跑
**335 秒且失败**、第二次 398 秒、第三次 309 秒 —— 每一次都"失败 + 回退"，而账号本身一直是好的。

**根因（三个，都在写入路径上）**：

| # | 现象 | 真因 | 代价 |
| --- | --- | --- | --- |
| 1 | 5 颗模组全部 `DestinySocketAlreadyHasPlug`（1679） | 上游把"这个槽已经装着它了"包在 **HTTP 500** 里回；`equip_build` 的模组循环把 `ErrorCode != 1` 当失败 | 每颗白花 ~10 秒（500 + 4 次退避重试），且触发整条回退 |
| 2 | 子职业插槽也一路 1679 | `execution_subclass` 就是**按当前配置**读出来的，于是每次 `equip_build` 都在重写一遍同样的 plug | 同上；**每次装备都必然失败并回退** |
| 3 | 预检里"这一位装不上"的一颗模组**抛错** | `_prepare_mod_operations` 遇到组件 207 清单里没有的模组直接 `raise TransferError` | 整条 `equip_build` 失败 + 回退 **~4 分钟**（与 ADR-013"装备照换、这一颗如实报"的口径相反） |

回退本身也不便宜：5 件搬回仓库 + 装回原来的护甲 + 逐颗恢复模组 + 回读核对，实测 **~215 秒**。

**改了什么**：

- `plug_already_installed()`（`services/loadout_mod_sockets.py`，**单一出处**）——1679 = 想要的状态已经成立。
  三条写入路径（`equip_build` 模组、子职业 plug、`equip_mod`）共用它；
- 预检把"这一位装不上"的模组标成 `blocked`（`ModOperation` 带 `reason`）而不是抛错：**跳过这一颗、
  不回退整条配装**，回执里说明原因与插入条件；
- 预检与子职业写入**先比对现状**：已经装着的那颗**根本不调用上游**（省掉那次注定 1679 的写入 + 重试）；
- `steps` 里写**模组名字**而不是 hash（它是调用方唯一的写后证据），有 blocked 时摘要改成
  "配装已装备，但有 N 颗模组装不上"并把原因放进 `warnings`。

**改后实测（同一支脚本、同一天、真机）**：

| 阶段 | 改前（失败那次） | 改后 |
| --- | --- | --- |
| 护甲快照 | 12.1 + 3.5 秒 | 10.1 + 2.7 秒 |
| 回滚快照 | 4.1 秒 | 2.9 秒 |
| 搬运 + 模组 | 26.9 + 69.4 秒（两次：写入 + 回退重装） | **52.8 秒**（一次） |
| 回读核对 | —（没能走到） | 6.3 秒 |
