# 求解器"最优性与极限"改造计划

一句话：**现在的求解器算得准，但目标函数只奖励"刚好达标"**；这份计划把它改成"先证明能不能，
再按优先级把能拿的都拿到"，并且把"这套装备到底能到哪"如实报出来。

对照物（外部两家都读过了，证据在各自小节里）：DIM 的 armor 求解器、`MIGO-OvO/d2-armor-solver`
（v3.x，MIT）。两家在同一个问题上给了一致的答案，这份计划按他们的口径 + 我们现有的机器来排。

> 本文记**取舍与实测证据**；最终定下来的对外口径另写一条 ADR（落地时取当时的最大号 +1，
> 见 `docs/adr/README.md`），别把两件事混进同一个文件。

---

## 一、现象（全部是本次会话的真机数据）

用户报："属性不是最优解，而且不够极限。"

拿"赫沃斯托夫星火术士"那套（术士，异域 星火协议，套装 埃希恩记忆 4 件）当样本：

| 项 | 值 |
| --- | --- |
| 社区模板要求 | 生命 0 ｜ 近战 70 ｜ **手雷 100～200** ｜ **超能 80～100** ｜ **职业 70～100** ｜ **武器 100～200** |
| 那次求解输入的硬目标 | weapons 100 / grenade 100 / class 70 / melee 70 / super 80，`priority_stats=["grenade","weapons"]` |
| 求解器自报 | `completion_rate: 1.0`、`requires_tuning: false`、`tuning_changes: []` |
| 实际装出来的六维 | 武器 107 / 生命 7 / 职业 71 / **手雷 120** / **超能 110** / 近战 71 |

三件事一眼可见：

1. **每项都趴在底线上**：手雷 120 落在 100~200 的两成位置，武器 107（7%）、职业 71（3%）、近战 71（刚过 1 点）。
2. **超能 110 超过了模板上限 100 十点**，而我们全程没有报过任何"违规"——因为我们**根本没有"上限"这个概念**。
3. **免费的额度没用**：五件护甲各有一个 0 能量的调谐槽，谁都没动过。

### 那条"至少能多拿 10 点手雷"的算术证据

不动装备、不动模组，只把头盔和腿的调谐从 `+超能/−生命值` 换成 `+手雷/−生命值`
（插件存在、0 能量、`plugCategoryIdentifier` 就是调谐槽那一类）：

- 手雷 120 → **130**；超能 110 → 100（要求只要 80）；其余五项一字不变；
- **仍然满足那次请求的全部硬目标** —— 也就是说求解器交的解，在它自己的目标下就不是最优的。

调谐插件表（plug set 1155052024）实测共 32 条：`平衡调整(+1×6)` 1 条 + 30 条 `+X/−Y`（各 +5/−5）。
五件全换理论上限是 +25 手雷，但会撞到"职业刚好 71→66 < 70"这类约束，所以真实可拿的是十几点量级，
需要求解器自己算，不能靠人眼估。

## 二、根因（四条，逐条给代码位置）

### 1. 非优先属性的天花板被压成了底线 —— **P0 更正：这不是"刚好达标"的原因**

`destiny_mcp/build/solver.py:224-233`：

```python
if priority_indices:
    desired_max = [
        MAX_STAT if index in priority_indices else desired_min[index]
        for index in range(6)
    ]
else:
    desired_max = [MAX_STAT] * 6      # 没给优先级时，六项都允许吃能量
```

只有 `priority_stats` 里点过名的属性拿到 `MAX_STAT`，其余**上限就等于下限**。这个 `desired_max`
被 `build/process_utils.py:413-430` 用来算 `max_added_stats`，于是那些属性的"还能加多少"恒为 0
——**剩余能量在它们身上一分都花不出去**。

**P0 更正（2026-09-21，读码 + 基准实测）**：这一条是**有意的设计**（"没要求就别浪费能量"），
不是"刚好 120/107"的原因。真正发生的是：**能量已经被下限吃光了**。那套配装的
武器要 100（词条只给 65）、职业要 70、近战要 70 全是紧约束，
`武器模组×3 + 职业模组 + 小型近战模组` 把 5 个通用槽全占满，手雷（已经 120 > 100）**没有余量可分**；
六点闲置能量也因此不可用 —— 任何一个通用槽换手雷都会让某项跌破下限。

反证：`titan_meets_minimum`（同样的目标口径、手雷优先）实测跑到
**武器 105 / 生命 0 / 职业 70 / 手雷 130 / 超能 80 / 近战 70** ——
说明"优先级会真的把属性顶到能量允许的最高"这条机制是有效的。
所以"不够极限"的真实来源是下面第 3、4 条 + 输入（见 P0 记录），不是 `desired_max` 的写法。

注意 `process_utils.py:401` 的注释写着 `desired_max_stats: Maximum stat targets (0 = ignored)`：
**机器本来就有"上限"这个东西**，是我们喂错了值（喂成了下限）。P2 要做的是给它真正的上限来源。

### 2. 评分反过来奖励"贴底线"

`destiny_mcp/build/scorer.py:52-66`：

- 超出目标的部分：**每点罚 0.5**（且只对非优先属性算）；
- 六维总分：**每点只加 0.1**。

净效果就是"越贴近下限分越高"。而 `services/build_results.py:130` 的
`completion_rate = 达标条数 / 目标条数`，候选排序又以它打头 —— 一层层下来，
"多堆 10 点手雷"在整套评分里是**负收益**。

外部对照：`d2-armor-solver` 的 `docs/priority-rules-audit.md` 自查出同一族的病
（一个高优先级 `≤100` 的属性取 80 时反被扣分，结果"规则说别超过 100，排序却把它往 100 推"），
它的结论原话是 **"达标与贴近输入值不是一回事"**，并明确要求"统一搜索评分、下界剪枝、
库存/升级比较器与展示排序，**不要仅调大数权重**"。

### 3. 调谐没进搜索域

`services/build_tuning.py` 的调谐只在**目标没达成**时才被当成补救手段动用（`requires_tuning`），
所以这次的 `requires_tuning=false` + `tuning_changes=[]` 是"设计如此"而不是巧合。
DIM 的 `mappers.ts:135-183`（`buildTuningVariants`）和 d2-armor-solver 的
`docs/complete-optimization.md`（"Every eligible piece can leave its Tuning socket empty"）
都把调谐（含"空着"）当作搜索域的一部分。

### 4. 两套排序口径并存（同一个事实写了两遍）

- 搜索内部：`solver.py:49-63` 的 `_ranking_metric` = **优先级字典序在前、总和在后**；
- 最终展示：`scorer.py` 的加权分 + `build_results.py` 的 `completion_rate` 打头。

两者对同一个问题给不同答案。这正是 d2-armor-solver 那份审计的结论
（"只更改一个 UI 排序函数不能统一搜索、剪枝、候选保留与最终展示"）。

### 附带发现：已有的"能到哪"机器全都在无解路径里

- `build/analyzer.py` 的 `_max_possible_stats`：逐属性上限（"把点全堆这一项"）；
- `tools/_armor_ladder.py`：`ceiling`、`single_stat_ceiling`、`shortfall`、`trials`、`tuning_first`；
- `build/process_utils.py:452` 的 `update_max_stats`：求解过程中已经算出可达值，但**没进响应**。

**P0 补充（读码确认）**：`solver.py:505` 初始化 `stat_ranges`、`604-613` 每套组合都喂给
`update_max_stats` 让它更新，**然后这个变量再也没被读过** —— 是一段纯粹的**死计算**。
也就是说"可达区间"不仅算法有了，连每次求解都已经算过一遍，只是被丢掉了。P2 主要是**接线**，
不是新数学。

也就是说"报可达区间"这件事**不需要新的数学**，主要是把它从"只有无解时才跑"升格成
"有解时也给"，并按 DIM / d2-armor-solver 的既有纪律配一句免责
（**逐项可达 ≠ 同时可达**，我们语料第 382/396 行已经钉了这句话，别丢）。

## 三、口径决定（要拍板的五件事，都带我的推荐）

### 决定 1：目标有三种语义，不许再混

| 语义 | 含义 | 现状 |
| --- | --- | --- |
| **下限** | 硬约束，必须满足 | 有（`*_target`） |
| **上限** | 超了算违规（会被排到后面并标注），但**不阻止出解** | **完全没有** |
| **偏好** | 都达标之后，按这个顺序尽量高 | 有名字（`priority_stats`），但被 `desired_max` 的写法废掉了 |

**推荐**：三个都保留、各司其职。区间 `100~200` = 下限 100 + 上限 200；"尽量高"用偏好顺序表达。
**被否**：把区间上限当硬约束（模板超了不该"无解"，游戏里超上限也没有惩罚）；
把"只要给了区间就自动冲到上限"当默认（DIM 和 d2-armor-solver 都不这么做，用户没要就别猜）。

### 决定 2：排序口径统一成一份，逐字段字典序，删掉浪费惩罚

按 d2-armor-solver 的 9 元组（`src/core/stat-ranking.mjs`）：

```
[有没有任何显式规则没满足, 高优先未达标个数, 高优先缺口, 中…, 低…, 普通…]
```

要点：① 第一位是**布尔**，不是跨层加权；② 同层**先比未达标个数、再比缺口**；
③ 字典序逐字段比 → **低优先级的富余不能补贴高优先级的缺失**。
之后才比刷取成本 / 稳定性。

**推荐**：照抄这个结构，并且**搜索、剪枝下界、候选保留、展示四处共用同一个比较器**。
**被否**：继续用加权分再调权重（d2-armor-solver 试过，明确写了"不要仅调大数权重"）。

### 决定 3：阶段分离 —— 预算用尽永远不能产生"无解"

`feasibility（穷尽，不许被 top_n/超时截断）→ ranking（预算内排序取前 N）→ refinement（剩余时间精修）`，
响应里带 `coverage.complete`。d2-armor-solver 原文：**"no limit can create an infeasibility proof"**、
**"截断不能证明不可行"**。

**推荐**：照做。我们已经有 `analyze` 在没有验证过的情况下断言过"没有合法组合"的前科
（0.1.13 修的），这条守门是防它复发。

### 决定 4：不给偏好时怎么办

**推荐**：不猜 —— 只保证达标，**但响应里必须给出每属性的可达区间**，让用户一句话就能要"顶"。
理由：没要求就不优化（本仓库既有原则），同时把"能到哪"摆在眼前，用户不会再觉得工具"不够极限"。

### 决定 5：调谐进搜索，但分两条路走

全枚举调谐域是 32 种/件（含"空着"），五件就是 32⁵ —— 术士本身已经要 ~190s，不能硬上。

**推荐**：
- **便宜路径（默认走）**：达标之后按偏好顺序，逐件把调谐换成 `+偏好/−代价`、把剩余能量吃满，**不枚举**；
- **昂贵路径（显式要"顶到极限"或要证明某条线可达时才走）**：枚举调谐域（含空着）做可达性判定。

**被否**：默认全枚举（术士会撞预算）；把调谐留给用户自己进游戏改（那正是现在的问题）。

## 四、阶段计划

每阶段独立可交付；**P0 不做完不许动 P1 之后的任何一步**（"声称之前先量"）。

### P0 先量：基线 + 可复现基准

- **交付**
  - `scripts/benchmark_build_solver.py`：对"当前 checkout 或一个隔离的 git ref"跑同一批用例，
    逐行输出 JSON（子进程跑，父进程聚合），不写对方的目录。
  - `docs/benchmarks/build-solver-<label>.json`：落盘的结果（含 node/硬件信息）。
  - `scripts/capture_weapon_baseline.py` 增加 `build` 面（或单开 `capture_build_baseline.py`）
    + `tests/baselines/build_responses/` + `tests/test_build_baseline.py`：求解器响应目前**没有**
    基线 diff 闸门（护甲/武器都有），P1 之后要动排序，没有对照物等于摸黑。
- **指标**：`wallMs`、`status`、`candidateCount`、`targetsMet/targetsTotal`、`finalStats`、
  `coverageComplete`、工作量计数（`combos`）。**P0 已确认 `combos` 不用新加**：`solver.py:507/530`
  已经在数、`ProcessResult.combos`（`process_types.py:146`）已经在返回，只是服务层
  `solve_with_tuning` 只回 `(pool, tuning_map)` 把它丢了 —— 基准脚本绕开服务层直接调 `solve()`
  拿这个数（同一次运行里同时量端到端与内核两条路，见下）。
- **口径**：配对**交替顺序**跑三次取中位；无解时"首次解耗时"记 `null` **不是 0**；
  只给**确定性工作量**对比，秒数只作参考；文档里明文写"哪些历史数字不作为证据"。
- **验收**：一条命令能复现"手雷 120 / 武器 107 / 超能 110"和术士 `find` 的耗时区间。
- **风险**：基准本身别把机器跑爆 —— 术士那两条用例单次 ~190s，默认集里不放，`--heavy` 才开。

### P0 成本剖面（实测，这条改写了性能部分的取舍）

`docs/benchmarks/build-solver-p0-baseline.json`（3 用例 × 3 次取中位）：

| 用例 | 端到端 | 内核 `solve()` | combos | 顶层六维 |
| --- | --- | --- | --- | --- |
| `hunter_priority_only`（只有优先级） | 18.0s | 12.4s | 6,283,200 | 武器102 / 生命14 / 职业80 / **手雷190** / 超能35 / 近战4 |
| `titan_meets_minimum`（六项下限 + 手雷优先） | 7.8s | 5.3s | 3,876,000 | 武器105 / 生命0 / 职业70 / **手雷130** / 超能80 / 近战70 |
| `hunter_priority_set`（金装 + 高目标 150/100/80/70/70） | **283.2s** | 0.25s | 75,712 | 武器150 / 生命6 / 职业116 / 手雷70 / 超能80 / 近战71 |

两条结论：

1. **"不够极限"的机制是好的，被下限挡住了。** 不给下限时手雷能被顶到 **190**；给六项下限但手雷优先时是 **130**。
   术士那套只有 120，是因为武器/职业/近战三项下限把 5 个通用模组槽占满了 —— 与"机制失灵"无关。
2. **贵的地方不是枚举，是"严格解为空 → 调谐补救"那条路。** 同一个请求分段实测
   （`scripts/_probe_find_build_cost.py`，一次性探针，已删）：

   ```
   get_armor_snapshot    6.51s  (118 件)
   _parse_constraints    0.02s
   solve() 内核          0.27s  combos=75,712 sets=0     ← 严格解一个都没有
   solve_with_tuning   212.66s  pool=2 tuning=2          ← 全在这儿
   _build_results        0.02s
   ```

   **补救路径是枚举的 ~800 倍。** 这直接决定 P4 的做法：把调谐塞进主搜索**不能**是"再套一层枚举"，
   得复用/替换这条补救路径；也说明 `hunter_infeasible`（无解，75s）与术士那两条（~190s）
   都属于同一类花钱的地方。默认用例集因此按成本拆开：默认只留枚举主导的两条（~26s 三遍），
   其余进 `--heavy`。

3. **本会话那套（术士 + 星火协议 + 埃希恩记忆 4 件）实测只要 9.2s**，不是语料里记的 ~190s：

   ```
   warlock_khvostov   端到端 9208ms | 内核 5797ms | combos 3,769,920
   → 武器107 / 生命12 / 职业71 / 手雷120 / 超能105 / 近战71
   ```

   手雷 120 与身上那套**一致**（现象复现 ✓）。语料第 139 行那句"术士 ~190s"是**没有金装/套装收窄**
   时的数，别拿它当这套的预期；P5 更新语料时顺手改正。
   顺带：求解器自己给的头名是 生命12/超能105，身上装的是 生命7/超能110 —— 两项合计都是 117，
   差的就是调谐槽往哪边偏（这正是 P4 要让它自己算干净的那点空间）。

4. **把目标抬到 130 它就能给 130 ——"不够极限"确实是"没人要求"**（`docs/benchmarks/build-solver-p0-heavy.json`）：

   | 请求 | 端到端 | 内核 | combos | 结果 |
   | --- | --- | --- | --- | --- |
   | 手雷 ≥100 | 9.2s | 5.8s | 3,769,920 | 武器107 / 生命12 / 职业71 / **手雷120** / 超能105 / 近战71 |
   | 手雷 **≥130** | **140.0s** | 5.7s | 3,769,920 | 武器102 / 生命12 / 职业71 / **手雷130** / 超能100 / 近战71 |

   内核工作量**一模一样**（同一批组合），差的是端到端 9.2s → 140s：第二条走了
   "严格解为空 → 调谐补救"那条贵路。所以：
   - 我之前手算的"免费调谐还能多拿 10 点"**由求解器自己证实了**（它能在别项仍达标的前提下给到 130）；
   - **P2 要做的是让用户能表达"我要顶"**（区间上限/偏好），**P4 要做的是让这个"顶"别再花 140 秒**。
     这两条合起来才是"够极限"，而单看算法它早就够得着。

5. `hunter_infeasible`（真无解）端到端 27.8s、内核 10.6s、0 候选。**注意这条量的是服务层**，
   工具层的 `ladder` 还会再补几次 `analyze`/`recommend`（护甲基线里同一形状的工具调用记的是 75s），
   所以"无解"的用户体感成本比这里高 —— P1 做 `coverage.complete` 时要连这条一起量。

6. **一条未归因的成本漂移，记在这儿别忘**：同一个请求（猎人 + 快速装弹松身裤 + 150/100/80/70/70）
   在护甲基线里记的是 **75.6s**（`tests/baselines/armor_responses/index.json` 的 `ladder_no_solution`），

   按日期找当时的 commit → `git worktree` 出来 → 用同一条基准用例 paired 跑一遍。

**尚未在 P0 里做**（留给后续阶段，别当成已完成）：

## 四·六、P1 落地记录（2026-09-22）

**先查清了"今天到底会不会说谎"**，结论是：**不会，而且原因是可指认的**。

`[]`（0 候选）在今天的实现里确实是"枚举完了、没有任何一套能满足下限"，因为：

1. 五层枚举**没有配额**（`solver.py:509-652` 是完整笛卡尔积，`combs` 只用来计数）；
2. 补不上下限的组合在**进堆之前**就被 `validate_fixed_process_items` 拒掉
   （`solver.py:600-602`，它内部真的跑一次模组分配，`pick_and_assign_slot_independent_mods`
   拿 `needed_stats` 当目标，补不上返回 None）——所以堆里**只有**满足下限的解，
   top-N 截断挤不掉"唯一那套达标的"；
3. 唯一"搜不了"的状态（组合规模超限）走 `BuildTooLargeError` → 工具返回 `not_computed`，不是"无解"；
4. 超时走 `BuildValidationError` → 错误响应，也不是"无解"。

**实测证据**：构造 3125 套组合、其中 3124 套"优先级高但永远达不到下限"、唯一达标那套在优先级上垫底、

把"能否满足下限"从"进堆前的校验"挪到"进堆后的排序"，它会立刻变红（注入验证过）。

**交付**：

- `build/process_types.SearchCoverage` + `ProcessResult.complete/truncated_by`：

## 四·七、P2 落地记录（2026-09-22）

**交付**：

- **上限（`stat_caps`）**：`BuildRequest.stat_caps` → `BuildConstraints.*_max`（0 = 不限）→
  `prepare_fixed_set_context` 的 `desired_max`。给了上限时，`desired_max` 取
  `max(下限, 上限 − 碎片/子职业加成)`；只有部分属性给了上限时，没给的优先项照旧吃满，
  没给的非优先项照旧压在下限上。
- **超上限的处置**：`HeapEntry` 最前面加 `caps_ok`（1 = 没超）。min-heap 里元组越小越差，
  于是超上限的方案自动沉底、被优先挤出。`could_insert` 相应改成**保守**判定
  （`caps_ok` 不同就先比它，相同再比总值）—— 不这么改会漏判：
  一套"没超上限但总值低于超上限的堆顶"的方案其实进得来，按老写法会被剪掉，那就是 P1 说的假无解。
- **逐项可达**：`stat_ranges` 那段死计算（形状 `[[MAX_STAT, 0]]*6`，`[0]` 永远是假的）改成
  只维护上限的 `reachable_ceilings`，经 `ProcessResult` → `TuningOutcome` → `SearchDiagnostics`
  一路到 `data.reachable`。
- **输入校验**：不认识的键 / 超 0-200 / 上限低于下限 → `build_validation_error`。
  上限**不许静默忽略**（忽略了用户会拿到自己声明过不要超过的配装，且看不出哪里错了）。
- 参数面：`stat_caps` 登记进 `_param_contracts`（求解类 intent）+ `_param_docs`，
  `routing.md` 的参数表重新生成（`python -m destiny_mcp.tools._param_contracts --write-doc`）。

**两处与计划的偏差，都是实测逼出来的**：

1. **"上限进剪枝界"这条没做，而且是**故意**不做**：它和决定 1 的"超上限不阻止出解"直接冲突
   （按上限剪枝会把唯一那套解剪没）。上限只进 `desired_max`（模组不再往上堆）+ 排序位 + 标注。
   计划里那句验收口径作废，以这里为准。
2. **`reachable` 不是"上限"，是"已验证能到的保守下界"**。真机实测打脸：
   同一组约束下 `reachable` 报手雷 **120**，但把手雷下限写成 **130** 时求解器确实能给 130
   （而且那套 **超能正好 100、不超上限**）。原因是这一步按 +1 粒度试算，而它依赖的
   `choose_auto_mods` 是**贪心**的（DIM 那边是精确枚举），要求 +1 时可能装不下、于是提前 break。
   所以措辞定成"保守下界"，两句免责（保守下界 / 逐项可达 ≠ 同时达到）都写进了
   `reachable_note` 并由守门钉住。**要变成真上限，得让这一步走精确枚举 —— 成本上升，
   留给 P4 一起量。**

**真机验收**（术士 + 星火协议 + 埃希恩记忆 4 件，模板六项原样：下限 生命0/近战70/手雷100/超能80/职业70/武器100，
上限 手雷200/超能100/职业100/武器200）：

```
找到 3 个候选配装。其中 3 套超过了指定的属性上限（见各自的 max_violations），已排到没超上限的方案后面。
reachable: {weapons 107, health 12, class_stat 76, grenade 120, melee 76, super_stat 110}
候选0: 武器107 生命12 职业71 手雷120 超能105 近战71  ← max_violations: 超能 105 > 100
把手雷下限抬到 130（同样 caps）：
候选0: 武器102 生命12 职业71 手雷130 超能100 近战71  ← **不超任何上限**
```

两条结论：① **上限真的会被报出来**（以前 110 > 模板上限 100 没人吭声）；
② "顶上去"和"不超上限"**可以兼得** —— 只要说清楚要哪个。这也再次印证 P0 的判断：
"不够极限"是**没人要求**，不是算法够不着。

## 五、明确不做的事

对照两家读完之后的取舍（**不做也是决定**，写在这里免得被反复提）：

1. **worker / 多进程并行**：d2-armor-solver 自己的实测是反例 —— 14 个 worker 让 388ms → 1056ms、
   内存 ×16、主线程延迟 29ms → 417ms，所以他们定成 Fast/Balanced 强制单分片、只有 Deep 才 4 片。
   我们求解是秒级到百秒级、候选集小，多进程 clone 库存 + 全库复核只会更贵。**提速先做界与顺序。**
2. **整库数学等价类压缩**：只在 1300 件大库且要先解决"搜索顺序即契约"才划算。
   只借其中一条：**否定结果由等价类共享**。
3. **完整宏等价（plan-equivalence）**：那是"库存规划器"的需求。只借一条：
   `精工/调谐按六维贡献向量比较，不按数量比较`（不同件的精工三属性不同）。
4. **400 万条的密集 adjustment 表**：只适合"精确点目标 + 固定五件"的常数级查询。
5. **一次给 200 套解 / DIM 式 UI**：我们是 MCP 工具，用 `top_n` + **可达区间**表达，
   不做并排对比界面。
6. **不改 `equip_build` 的"确认后写入"纪律**：不管排序怎么变，写入仍需用户明确确认。

## 四·八、P3 落地记录（2026-09-22）

**交付**：新增 `build/ranking.py`，排序口径收到一处；四处共用它。

键的形状（**别照抄参考实现的"高/中/低三层"来理解**）：

    [有没有任何显式规则没满足（布尔）]
    + 每个 priority_stat 各一层 × (未达标个数, 缺口)
    + 普通层（没进 priority_stats 的项）× (未达标个数, 缺口)
    + 优先级值（按顺序）
    + 封顶后的六维总和

三处要说清的地方：

1. **"先个数后缺口"只在普通层真正起作用** —— 每个优先项各占一层，那层的个数只可能是 0/1，
   等价于"先看达没达、再看差多少"。参考实现固定三档、可以让多项同档，所以那里这条性质更吃重。
2. **布尔位其实是冗余的**：任何违规都会在它所属那层留下负数，干净的方案那里是 0，
   逐字段比下来干净的必赢。留着是把"先看违规"写成显式契约（也便于早退），不是唯一防线。
3. **`score` 不再是排序键**：它改成"封顶后的六维总和"（超上限不计）。真机交叉验证：
   三个候选的 `score` 是 481 / 468 / 471，而展示顺序是 481、**468**、471 ——
   手雷 120（总分 468）排在总分 471 之前，因为优先级第一项是手雷。这正是"优先级优先、
   不按总分"的预期行为；旧口径下 `score` 是最后一层 tie-break，不可能出现这种顺序。

**改动面**：`solver`（剪枝用乐观键 `goodness_key(..., span=max_mod_bonus)`、落库用真实键）、
`HeapEntry`（三个排序字段 + P2 临时加的 `caps_ok` 收成一个 `rank_key`）、
`rank_results()`（展示层唯一入口，`build_service` 只调它）、`scorer.score`（降级为展示）、
`farm_target`（属性那一段改用共享的 `priority_desc`；**它自己的刷取成本键留在本地** ——
"要改几件/调谐几次"是反推待刷件的目标，与"哪套属性更好"不是一回事）。

**守门**：`tests/test_build_ranking.py` 12 条，含 d2-armor-solver 公开自查里的现成反例。
注入验证 **4 条咬住、1 条故意不咬**：

- 咬住：缺口不参与判定 / 普通层顺序颠倒 / 展示排序换成 score / 优先级分层退化成全局汇总；
- 不咬的那条是"低优先富余不能补贴高优先缺失"：这个方向由**两处机制同向**保证
  （每层规则 + 优先级偏好），单点注掉任何一处它仍然绿。所以那条守的是**性质**，
  我在测试里写明了这一点，避免下一个人误以为它是单点守门。

**两个过程记录**（都是教训）：

- `farm_target.py` 卡在 1296 行上限，我加注释把它顶到 1300 → 按仓库规矩**压缩注释**回到 1294，
  没有抬上限。动这类模块之前先看 `tests/test_module_size_ratchet.py`。
- 真机冒烟时看到"手雷 110 排在手雷 120 前面"，按"先算键再下结论"查了一遍：
  **是我那个一次性探针里 `KEYS` 把 `melee`/`super_stat` 写反了**（`STAT_NAMES` 顺序是
  `…grenade, melee, super_stat`），产品代码没问题。教训：喂给排序函数的手写向量，
  顺序必须来自 `STAT_NAMES` 这个单一出处，别手抄。

### 成本漂移归因：结案（不是回归，是行为变了）

P0 记录里那条"同请求 75.6s（护甲基线）→ 238.0s（今天）"的漂移，按日期找回当时的 commit
并用 paired 基准跑完了，结论明确：

| 版本 | commit / 日期 | 同一请求（猎人 + 快速装弹松身裤 + 150/100/80/70/70） | 耗时 |
| --- | --- | --- | --- |
| 0.1.2（**没有调谐补救**） | `353bba8` / 2026-09-13 | **0 候选**（`solve()` 245ms / 75,712 组合不变） | 端到端 **6.5s** |

| 今天 | `9063a9c` | **2 个候选**（靠调谐救回来） | 端到端 **283s**（其中补救 212s） |

- **枚举那一段一点没慢**（75,712 组合、245ms，两版一致）；
- 多出来的两分多钟是**新能力的价格** —— 同一请求以前"配不出来"、现在"配得出来但要过一遍
  放宽目标 + 逐套复核"；
- 于是 P4 的目标也就清楚了：**同样的答案（或更好的），不该花 200 秒**。

## 四·九、P4 落地记录（2026-09-22）

**交付：便宜路径**（`build/tuning.py` 的 `local_tuning_improvement` + 批量入口
`improve_pool_with_local_tuning`，服务层 `apply_local_tuning` 挂在 `find_build` 上）：

- 在**候选池**上做"单件调谐"邻域贪心：每步试 5 件 × 该件选项，**每一步都过
  `validate_fixed_process_items`**（按真实目标重排属性模组再比六维）—— 与补救路径同一判据；
- 选项先按"可能变好"过滤（提升某个优先项 / 把超上限那项降下来 / 抬高封顶总和）。
  这个过滤是**安全的**：只动非优先且都在区间内、又不改封顶总和的走法，在排序键上不可能变好；
- **对外只报净改动**：贪心可能对同一件走好几步（第一步 +手雷/−生命值，第二步发现那一项
  已经见底、换成 +手雷/−超能 是白拿的）。真机第一次跑报了 12 条、实际只涉及 5 件 —— 已收敛成
  "每件一条、从原样到最终样"。这条是守门测试抓出来的。
- **用户什么都没要求时不动他的调谐**：调谐免费，但"改 5 件"要他自己动手点。没有目标也没有
  优先级时，唯一还能提升的只剩排序键最后那位"封顶总和"（平衡调整 +1×6）—— 为 +6 让用户改 5 件
  不是他要的。真机第一次跑就出现过这个噪音。

**真机验收（术士 + 星火协议 + 埃希恩记忆 4 件，手雷下限 100、超能上限 100）**：

| | P4 前 | P4 后 |
| --- | --- | --- |
| 端到端 | 9.2s（P0）→ 283s（调谐补救那趟） | **17.6s** |
| 手雷 | 120 | **145** |
| 超能 | 105 / 110（超上限） | **95**（不超上限） |
| 净改动 | 无 | 2~4 件调谐 |

验收线是"手雷 ≥ 130"，实测 **145** —— 而 P2 时我手算的"免费额度上限"正好是 +25 点（120→145）。
也就是说：**那 25 点在调谐槽里躺了一整轮，现在默认就能拿到**。

**两条边界（都是实测得出结论，不是推测）**：

1. **便宜路径救不了"严格解为空"**。同批的 `hunter_priority_set`（金装 + 150/100/80/70/70）
   端到端仍是 **292.8s**，其中内核（枚举 75,712 组合）只有 0.76s —— 钱全在
   `solve_with_tuning` 的"放宽目标复解 + 逐套精确复核"上。那条路**这次没动**：
   P4 的计划口径是"便宜路 + 昂贵路分工"，没有承诺替换补救路径。它现在是**最大的单项成本**，
   单列进待办（见下）。
2. **`reachable` 仍是保守下界**（P2 遗留）。这次不修的理由是实测的：既然"要顶到 X"只要把
   下限写成 X 就有答案（20s 级），再做一个昂贵的精确枚举路径就没有产品价值了。
   要修的是"那个数报小了"这一件事，而措辞已经说清（`reachable_note` 两句免责）。

**守门**：`tests/test_build_local_tuning.py` 6 条，注入验证 3 条咬住、1 条结构性保证：

- 咬住：贪心的基线必须用**当前**状态（第一版拿原始键当基线 → 会把已经变好的状态改回去，
  正是这条守门抓到的真 bug）/ 跳过净改动 / 什么都不要求时也动调谐；
- 结构性保证："每一步都过权威复核"—— 这个函数里只有一条求值路径，没有"拍近似值"的分支可注。
  我在测试文件里写明了这一点，免得下一个人以为它没守。

**两道 ADR**（对外口径在这里定死，不再散落在话术里）：

### 顺手把两件"长期挂着的不确定"变成事实（真机，一次往返）

写 P5 时发现 README、routing、两份计划文档、语料里都还写着「**调谐只能在游戏内改**
（实测 1663）」—— 那句的出处是 ADR-012 推翻的字段名 bug，**证据早就作废了**，只是没人回头改。
用户同意做一次真机往返（新增 `scripts/verify_tuning_write.py`，做法照
`verify_armor_mod_sockets.py`：换一颗 → 回读插槽 + 回读组件 304 的六维 → 换回原样）：

| 换成哪一颗 | 结果 |
| --- | --- |
| 身上**别的护甲正装着**的 `平衡调整`（3122197216） | **成功**：`ErrorCode=1`、回读插槽真变、换回也成 |
| 一颗**你没有**的 `+手雷 / -生命值`（455024236） | **1675**「负担不起这个动作的材料要求」，回读确认**账号一个字节没变** |

三条边角事实：① 角色的可插入清单（组件 207）**根本不覆盖调谐槽**——5 件护甲上正装着的调谐
一颗都不在里面，所以它不能当"这个调谐能不能换"的判据；② 免费接口能寻址这个槽（原样重插回
1679 `DestinySocketAlreadyHasPlug`，不是失败）；③ 换调谐**要材料**，所以"免费"只对能量成立，
对材料不成立。

**新的产品约束（进待办）**：调谐建议必须落在**用户已经拥有**的调谐上，否则给的是他做不到的方案。
现在的 `plan_tuning` 没有这一步筛选 —— 在补上它之前，谁都不许承诺"照这个改就能达标"。

### 真机对账咬出的第二个 bug：平衡调整的模型是错的

写入对账那一行（`实测变化` vs `预期变化`）当场不一样：

```
实测: 职业+1 近战+1 生命+6 超能-5
预期: 武器+1 手雷+1 职业+1 近战+1 生命+6 超能-4     ← 按"六维各 +1"算的
```

真机规则是 **`平衡调整` 只给"恰好三项并列最低"的那三项各 +1**（这一件：生命5/职业5/近战5；
30 的武器/手雷/超能一动不动）。`armor_rules.py` 的模板模型一直是对的、连文档串都写着，
但 `build/tuning.py` 的候选目录里是 `delta=(1,)*6` —— **同一个 plug 两套模型打架**，
而求解器搜索用的是错的那份。修法：规则抽成 `armor_rules.balanced_tuning_bonus` 单一出处，
目录里那份改成全 0 占位、真实增量由 `PieceTuning.choice_delta` 按件现算。
影响面：以前每项多算 1（总账最多虚高 6 点），而且换成方向型调谐时基础值会反推错。

### 第三个发现：贪心的上限本身就在"没吃干净"

P4 那条局部最优不变量在修完模型后变红了：第 13 步本来还能再涨。查下去不是模型问题，是
`max_steps=12` **跑满就停了**（不是"没有改进了"停的）。实测同一组夹具的收敛点：

| 上限 | 结果 key | 评估次数 | 残留可改进 |
| --- | --- | --- | --- |
| 12 | 405 | 1833 | 2 处 |
| 16 | 421 | 2433 | 2 处 |
| **20** | **427** | **2883** | **0** |
| 24 / 32 / 48 | 427 | 2883 | 0 |

默认上限按实测收敛点调到 **24**，并且新增 `TuningPlan.exhausted`：碰上限就是"没吃干净"，
必须标出来（`tuning_note` 里会多一句），不能默默少给。守门：不变量断言 `exhausted is False`
+ 一条"上限压到 1 必须翻 True"的可注入测试。

### P5 顺手量出来的性能回归（两条，都已修，数字是实跑）

P4 的交货数字是在**小池子**上量的（本会话那套 5 套候选），拿全量基准一跑就露馅了：

| 用例 | P0 | P5 改前 | P5 改后 | 说明 |
| --- | --- | --- | --- | --- |
| `hunter_priority_only` | 18.0s / 内核 12.4s | **156.8s / 95.0s** | **45.6s / 35.5s** | 纯枚举主导 |
| `titan_meets_minimum` | 7.8s / 5.3s | **130.3s / 8.0s** | **14.5s / 8.6s** | 服务侧主导 |
| `hunter_priority_set` | 283.2s / 0.3s | 389.8s / 0.3s | 未重测（补救路径没动） | 补救主导 |
| `warlock_grenade_130` | 140.0s / 5.7s | 218.2s / 4.6s | 见下 | 补救主导 |

**回归一：内核慢 7.7 倍（95s vs 12.4s）—— P3 那把键的代价。** cProfile 归因很干净：

```
ncalls       tottime   function
85771796    32.1s     builtins.getattr
2859018     25.1s     ranking.rule_rank          ← 按组合调用
8577085     17.9s     models.max_vector          ← 每个组合重建一遍常量！
5718057     12.4s     models.as_vector
39765728    11.0s     dict.get
```

`goodness_key` 被调 **286 万次**（按组合），而它每一次都要从 pydantic 约束上重新取
下限/上限/优先级 —— 这些量在整个求解过程中**是常量**。修法：新增 `RankingVectors`
（纯元组），在 `solve()` 里 **`vectors_for(constraints)` 只算一次**，内层全部传它。
公开签名不变（多个可选 `vectors=` 参数）。**内核：95.0s → 35.8s（2.65 倍）**。

剩下的 35.8s 对比 P0 的 12.4s 是**P3 的有意代价**：一把逐字段字典序的键比原来那个小
元组贵，换来的是"三套口径打架"这件事被消灭。这条不再优化 —— 要再快就得换剪枝策略，
那是另一个题目。

**回归二：服务侧多出 60–120 秒 —— P4/P5 的局部调谐吃得太宽。** 内核一次交回**整池 200 套**
（`RETURNED_ARMOR_SETS`），而 `apply_local_tuning` 逐套跑贪心 —— 用户看到的只有 top_n 套。
修法：加**候补窗口**（按当前 `rank_key` 取前 `max(2 × top_n, 10)` 套），其余原样带回。
这是**有意的成本取舍，不是证明**：窗口外的套理论上可能靠调谐挤进前 top_n，我们选了成本。
两条用例的 top 六维**一字未变**（`weapons110/health10/class75/grenade200/super85/melee20`
与 `weapons100/health15/class70/grenade165/super80/melee70`），端到端 **156.8→45.6s**、
**130.3→14.5s**。

**还没解决**：`hunter_priority_set`（389.8s）与 `warlock_grenade_130`（218–333s）都是
"严格解为空 → 放宽目标复解 + 逐套精确复核"那条路主导的，P5 没有动它 —— 它仍是最大的
单项成本，待办第 1 条指向它。

**这条用例本身就不稳**，写下来免得下一个人拿它当基准：`warlock_grenade_130` 同一份代码
四次实测 **140.0s（P0）/ 218.2s / 333.3s / 235.9s**，而 `combos` 三次都是 3,769,920（确定性计数一样）
—— 也就是说抖动全在补救路径上，它是**搜索节点数**驱动的，不是固定成本。归因线索：
P5 修了平衡调整的模型之后，`tuning_headroom`（每项最多能靠调谐加多少）**变小了** ——
旧模型给六维各 +1，于是任何差 1 点的项都算"平衡调整能补"；新模型只给最低的三项 +1，
于是有些项不再算有额度，救援搜索的走向就变了。**要动补救路径，先给它建一个稳定的
工作量计数器（`plan_tuning.searched` 已经有，只是没接出来），别再拿秒数当基准。**

## 四·十二、P6 真机验证（2026-09-22）

**脚本**：`scripts/verify_build_ceiling.py`（只读，三个场景用 `--scene` 选）

| 场景 | 请求 | 实测 |
| --- | --- | --- |
| `installed` | 术士 + 星火协议，手雷 ≥100、超能 ≤100 | 内核 **66.3s**（修剪枝前 **355s**，300s 预算**直接超时**）；候选超能全压在 100；`reachable` 武器181 生命181 职业161 手雷200 超能175 近战190 |
| `caps` | 社区模板六项按**区间原样**（生命0、近战70、手雷100~200、超能80~100、职业70~100、武器100~200） | **19.5s**、3 套候选，top `武器107 生命24 职业74 手雷120 超能100 近战77`，**超能正好 100、没有 `max_violations`** |

现装那五件的对照（护甲+调谐，**不含**属性模组与子职业）：`武器86 生命18 职业42 手雷150 超能135 近战28`
—— 逐件（武器/生命/职业/手雷/超能/近战）：光芒领主面具 20/0/5/30/30/5 `+超能/−生命值`、
逃逸艺术家 20/6/6/30/25/6 `平衡调整`、光芒领主胸甲 20/6/6/30/25/6 `平衡调整`、
光芒领主护腿 20/0/5/30/30/5 `+超能/−生命值`、至高碎片 6/6/20/30/25/6 `平衡调整`。

方案里的六维（含属性模组）比现装高：`武器107 生命24 职业74 手雷120 超能100 近战77`
（现装那套按同口径是 武器86+模组 生命18 职业42 手雷150 超能135 近战28）—— 注意**超能从 135 压到 100**
是本轮模板上限要求的效果，不是退步。

**P6 抓到的两个 bug（都已修、都有守门）**：

1. **300 秒超时**（`installed` 第一次跑就炸）：不是求解器算不动，是**乐观剪枝的上界太松**——
   `goodness_key(..., span=budget)` 把一份**共享**的模组余量按"每项各加一遍"算，6 项就是 6 倍。
   偏偏这条请求没有 `priority_stats`，排序键最后只剩"封顶总和"这一位能区分，
   于是几乎每个组合都过了剪枝、进了最贵的校验（重排属性模组 + 可达上限）：内核 **355 秒**。
   修法：余量按排序键顺序**贪心分配**（该预算下最紧的合法上界）→ 内核 **355s → 66.3s**，
   且 top 方案一字未变（key 尾 483 两次一致）。
   守门：`tests/test_build_ranking.py` 新增**保守性属性测试**（枚举小预算分给六项的全部方案，
   断言乐观键 ≥ 每个可达向量的真实键）。**这条测试当场抓到我自己第一版的分配 bug**：
   花在优先级项上的预算在"总和"里又被扣了一次 —— 上界算小 = 会悄悄丢解，
   只靠"看起来更快了"是发现不了的。
2. **0 候选时 `reachable` 报了一排 0**（`caps` 第一版场景撞上）：那些数来自"逐套候选推上限"，
   **一套都没验过时全是 0** —— 报出去读起来像"你哪项都到不了"，事实是"这次没量过"。
   按"缺值不编 0"把规则落到形状工厂（`SearchDiagnostics.to_dict`：全 0 = 没量过），
   工具层不再判第二遍。

**同批的另外两处**（记在 P5 记录里）：`could_insert` 的边界从 `>=` 改成 `>`（`insert` 本来就是
严格大于，打平的候选永远进不了堆，`>=` 只是让它们白跑最贵的那一步 —— 结果完全等价）；
`MAX_STAT` 从 `process_types.py` 收进 `build/constants.py`（`ranking` 也要用，
而它不能反过来依赖 `process_types`）。

## 四·十三、用户发现的口径 bug：夹 0 反推把"牺牲见底的项"变成了凭空长点（2026-09-22）

**症状**：用户对着方案问"臂铠为什么不选另一件？那件手雷和超能都更高"——顺着这个问题查下去，
发现方案给第一件臂铠（光芒领主手套 `6917530188462631525`）记的 生命5/手雷5/超能5 是**账面值**：
它的组件 304 明明白白是 生命−5/手雷0/超能0。

**根因（两步，缺一不可）**：

1. `PieceTuning.base_with()` 把 `base + delta` **夹在 0** —— 理由是注释里写的"游戏里属性不会变成
   负数"。于是"给一件生命基础值为 0 的护甲装 +职业/−生命值"被算成 生命 = 0（不是 −5）；
2. 下一步反推基础值 `_invert_tuning()` 做 `observed − current_delta` —— 把第 1 步夹掉的那 5 点
   当成了"本来就有"：`0 − (−5) = +5`。

贪心对同一件会走好几步，每"牺牲一项已经见底的属性"就凭空长 5 点。真机实测同一件：
`武器25 生命−5 职业25 手雷0 超能0 近战30`（进局部调谐时，= 304 真值）→ 出局部调谐时
`武器30 生命5 职业20 手雷5 超能5 近战25`，**多 15 点**（其中 5 点手雷、5 点超能落在用户真正关心的项上）。

**"游戏里属性夹在 0"这条假设本身是错的**：组件 304 如实报负数（`生命−5` 就写在那儿），
所以**模型必须等于游戏报的数**。修法：

- `base_with` 不夹 0；`_invert_tuning` 的不动点校验不夹 0；兜底路径不再拿观测值当基础值
  （那会把当前调谐**再加一遍**）；
- `plan_tuning` 搜索里那条"任何一项都不许变成负数"的硬规则删掉 —— 游戏允许把 −5 打在
  基础值为 0 的项上（304 就是证据），只按**目标**判合格与否。以前那条规则会把
  "牺牲一项没用的属性去补目标"整类走法判死；
- 新增 `PieceTuning.movable`（机器可读）与 `note`（人话）**同进同出**：反推不出基础六维的件
  `movable=False`，任何改法都返回观测值（宁可不动它，也不编改法）；服务层两处收 `tunable`
  的地方改成按 `movable` 过滤。

**守门（都做了注入验证：把夹 0 恢复回去 → 4 条红）**：

- `tests/test_tuning.py::test_piece_stats_change_by_exactly_the_tuning_delta` —— **真机数字当金标准**：
  那件臂铠的基础值必须是 武器25 生命0 职业20 手雷0 超能0 近战30，换成 +武器/−近战 之后
  必须是 武器30 生命0 职业20 手雷0 超能0 近战25（一项都不许多）；
- `tests/test_tuning.py::test_uninvertible_piece_is_not_movable_and_never_invents_stats`；
- `tests/test_build_local_tuning.py::test_running_the_local_pass_twice_does_not_invent_points` ——
  **幂等性哨兵**：第二趟不许再长点（旧实现每跑一趟就往上飘）。逐件对账"六维变化 == 调谐 delta"；
- 四条编码了旧口径的测试按新口径重写（"−5 打已经见底的项上是白给" → **不是白给，如实记 −5**）。

**真机复核（修正后的那套）**：候选[0] 从 手雷115/超能105 修正为 **手雷110/超能100**，
正好等于五件 304 之和；候选[1] 武器155 手雷140 超能125 同样逐项等于 304 之和 ✓ 不再有水分。

**顺带纠正一处文档**：`docs/plans/ARMOR_FORMAT_PLAN.md` 第 10 条（"调谐的 −5 打在本就为 0 的项上是
**白给**"）按上面这条实测**作废** —— 它是当时的推理，不是实测。

**还没能定死的一件事**（要用户在游戏里看一眼）：游戏**显示**的六维是不是按件夹 0。
API（304）不夹，我们的模型现在跟着 API 走；如果游戏界面把这种件显示成 0 且人物总属性不受那 −5 影响，
那"牺牲见底的项"在**总属性**上就是真的白给，我们要再调一次口径。已请用户顺手验证。

## 四·十四、每件的可调谐属性是**逐件**的：求解器一直在开装不上的选项（用户指出，2026-09-22）

**用户的原话**："这个 +5/−5 的模组在护甲上不是通用的，每一件护甲的调谐对象都不一样" ——
他拿术士身上两件**同名**的「光芒领主手套」举例：一件只能加**职业**、另一件只能加**近战**。

**真机核实（读组件 310 `ItemReusablePlugs`）**：

| 件 | 可调谐属性 | 310 里给几颗 |
| --- | --- | --- |
| 光芒领主手套 `…631525` | **职业** | 6（5 颗 `+职业/−X` + 平衡调整） |
| 光芒领主手套 `…019736` | **近战** | 6 |
| 光芒领主手套 `…655282`（仓库） | **生命** | 6 |
| 光芒领主面具 `…608169` | **超能** | 6 |
| 光芒领主护腿 `…938450`（仓库） | **职业** | 6 |
| 至高碎片 `…629544` | **武器** | 6 |
| **星火协议（金装）** | **任意** | **31** |

**根因**：Manifest 的调谐 plug set 是**全局那 32 颗**（真机：三件手套指向同一个 plug set、
内容一模一样），而"每件只开放某一个属性 +5 的 5 颗"这件事**只在组件 310 里**——
我们的护甲快照压根没请求 310（`ARMOR_SNAPSHOT` 是 102/200/201/205/300/304/305），
于是 `piece_tuning` 拿全局目录当选项，规划出"这件根本装不上"的调谐。用户就是这么发现的。

**修法**：

- 新增 `profile_components.BUILD_ARMOR = [*ARMOR_SNAPSHOT, 310]`；`InventoryService.get_armor_snapshot`
  **默认带 310**（这个方法的定位就是"求解器的数据输入"），不规划调谐的调用方
  （社区模板核对）显式 `with_tuning_options=False`。代价实测 **4.11 MB → 8.90 MB**（术士全账号护甲）。
  **没有**去改 `ARMOR_SNAPSHOT`（单件详情那条路不需要、不该背这 4.8 MB）。
- `Armor.tuning_option_hashes`（组件 310 那份清单）；`piece_tuning` 的选项 = 清单过滤后的目录
  （+ 永远可用的"撤掉"）。**读不到清单 = `movable=False` + 说明，只留"撤掉"** ——
  缺数据 ≠ 允许，不许再拿全局目录顶上。
- 守门：两件同名手套的**真机金标准**（A 只出 `+职业/−X`、B 只出 `+近战/−X`，
  `+武器/−近战` 必须不在 A 的选项里）+ 一条"读不到 310 就不可动"。两条都做了注入验证
  （无视清单 → 金标准红；缺数据当允许 → 另一条红）。

**复算（武器优先、手雷其次、埃希恩记忆 4 件不变）**：候选从"武器160/手雷115"这种带水分的数字，
变成**候选[0] 武器145 手雷111**、**候选[1] 武器140 手雷140** —— 因为"每件都能加 5 武器"从来
就不成立（只有至高碎片和金装能加武器）。这就是用户那句"你好像忽略了这个"值多少：
上一版方案里**五件统一换 `+武器/−近战`，其中三件装不上**。

## 四·十五、口径审计：把"模型眼里的护甲"和游戏自己的数据逐件对账（2026-09-22）

用户连着发现三个口径 bug 之后问的那句"为什么来来回回这么多次还是一坨"，指向的是**流程**问题：
我一直在看输出（候选、排序、耗时），从没审过输入。所以写了
`scripts/audit_armor_model.py`（只读，退出码可当机器检查）：把游戏自己的组件摊开，
用**独立的算术路径**（不复用 `InventorySnapshot.from_profile` 的解析）重算一遍期望值，
逐件对账。查的是六件事：

1. `Armor.stats` == 304 − 已装的属性/工匠模组；
2. `Armor.tuning_option_hashes` == 组件 310 那份逐件清单；
3. 装着的调谐必须在 310 的清单里；
4. 调谐反推（`base = 观测 − 当前调谐`）不许出现负数；
5. 大师档位：插件声明的 N ⟺ 模型的 `masterwork_level`/`is_masterworked`；
6. 词条重建：词条槽 + 大师档位 + 调谐 + 模组 == 304。

**结果（全账号 468 件）**：六项全部对得上 ✓；另有 60 件非 T5、54 件没有调谐槽的件
按设计不适用（我们只反推 T5）；还顺手拿到 **4 件"304 里有负数"的证据**
（`生命−5` / `近战−4` / `近战−5`），给"不许夹 0"那条口径添了证人。

**审计当场又挖出两个模型 bug（都已修、都有守门）**：

1. **大师加成是"档位"，不是"有/无"**。插槽那颗「升级护甲」在 Manifest 里声明的是
   **"六维各 +N"（N = 1–5 档）**，真机生效范围是**"非词条那三项"各 +N** ——
   又一次"声明值 ≠ 生效范围"。我们以前固定拿 `gear_tier`（=5）当加成，于是
   **只升到 1/3/4 档的一大批件永远反推不出来**（`roll_parse_error` 长期挂着）。
   真机证人：降临回音臂铠 `…539530`（楷模典范，3 档：词条 武器20/超能30/近战25 +
   非词条三项各 3 = 304 的 `20 3 3 3 30 25`）、伟大狩猎臂环（4 档）、坚忍克己（1 档）、
   至高碎片（5 档）、光芒领主手套 `…631525`（**0 档**，插槽只有能量标记、304 里确实没有 +5）。
2. **大师的"有/无"本身也不该看 T 级**（`is_masterworked = gear_tier == 5` 是错的）：
   0 档的 T5 件在那条规则下被当成满大师。现在两者都从**插件声明的档位**读。

**固定证人**（`tests/baselines/armor_witnesses.json`，29 件）：全账号是"浮动样本"——今天抽到什么
明天不一定还在，而模型改动需要**固定的证人**。清单按"每部位 × 每个大师档位 + 12 个词条原型各一 +
金装（调谐 0 颗与 31 颗两种）+ 非 T5（按设计不反推）"抽具体实例 ID 存仓库，每次审计**逐条点名**；
清单只记"查哪些件、为什么查它"，期望值永远来自游戏当场的数据（`--capture` 重抽）。
证人不在账号里了（分解/转移）会单独报出来，不会当成"通过"。

**审计脚本自己的两个坑（写的时候现学）**：① 它对 `平衡调整` 用了声明值（六维各 +1）而不是
真规则（最低三项各 +1）→ 25 件"重建差 3 点"；② 它把大师加成硬写成 +5 → 又 7 件对不上。
审计脚本自己也会犯错这件事，正好说明**为什么每条规则都要有多个证人 + 独立路径**。

## 四·十六、求解器以为"整件护甲的能量都能拿来装属性模组"（落地时才暴露，2026-09-22）

用户让把候选[1] 落地，装模组时撞上：光芒领主手套 `…019736` **容量 11、手臂模组已占 9**，
换 `武器模组`（3 点）要 `12/11` —— **装不下**。可求解器给每件都排了 +10 武器模组。

**根因**（代码位置很干净）：`armor_to_process_item` 里

```python
remaining_energy = max(0, int(getattr(armor, "energy_capacity", 0) or 0))
```

把**整个容量**交给了求解器。DIM 那套本来有"活动模组排列"（`activity_mod_permutations`）来扣这部分，
但我们的调用点是 `precalculate_structures(auto_mod_data, [], [], True, …)` —— **两个列表永远是空的**，
那套机制从没启用过。于是模型口径成了"每件护甲的全部能量都能装属性模组"。

**修法**：解析层算 `Armor.energy_used_by_other_mods`（已装的 `enhancements.v2_*` 里**非** `v2_general`
的那些 = 方案不会动、但确实占能量的部位模组），`armor_to_process_item` 给
`remaining_energy_capacity = 容量 − 这部分`。一般插槽里那颗**不算** —— 它会被替换掉，能量会还回来。
守门：`tests/test_armor_masterwork.py` 两条（真机那件的 11−9=2；数据对不上时夹到 0），注入验证过。

**修完的端到端验证（这次是"模型 == 现实"）**：修正后求解器给出的候选[2] 是
**武器135 生命23 职业38 手雷140 超能125 近战28** —— 和用户账号上**真实装出来的那套逐项一致**
（在修之前，同一个方案它报 140，那 5 点是排不出来的）。另外它现在能正确算出
"换用仓库那件手套副本 `…655282`（没有部位模组占能量）能到 **武器140**"。
