# 求解器基准数据

`scripts/benchmark_build_solver.py` 落盘的结果。**先看这份说明再用里面的数字** —— 没有口径的
性能数字比没有数字更糟（会被当成结论引用）。

## 怎么读

- **不是 timing 断言。** 秒数受机器负载影响，跨机器比没有意义。有意义的只有：
  同一台机器上的 paired 对照（`--compare`），以及 `combos` 这类**确定性计数**。
- 每条用例默认跑 3 次**报中位**，原始各次都在 `trials[]` 里。heavy 用例因为单次就几分钟，
  可能只有 1 次 —— 看 `trials` 字段的长度，别默认它是 3。
- **没解时相关字段是 `null`，不是 0。**（"没找到解"与"0 秒找到解"是两件事。）
- **两条路分开量**：`serviceMs` 走 `BuildService.find_build`（含 worker 进程开销、含调谐补救），
  `solveMs` 是直接 `solve()` 的纯枚举。两者差得多是**正常的**，差值本身才是信息。
- 用例集按**实测成本**拆成默认与 `--heavy` 两档，理由写在脚本头部的注释里。

## 文件

| 文件 | 内容 | 口径 |
| --- | --- | --- |
| `build-solver-p0-baseline.json` | 改动前的默认集（3 例 × 3 次） | P1–P4 的对照物 |
| `build-solver-p0-heavy.json` | `hunter_infeasible`、`warlock_grenade_130` | 1 次/例，贵的用例 |
| `build-solver-p0-warlock-100.json` | 本会话那套（术士 + 星火协议 + 埃希恩记忆 4 件），手雷 ≥100 | 1 次 |

P0 的关键结论（完整分析见 `docs/plans/SOLVER_OPTIMALITY_PLAN.md` 的「P0 成本剖面」）：

- 同一个人的同一批装备，**把手雷目标从 100 抬到 130，求解器就能给 130**（其余下限仍达标）；
- 但端到端从 **9.2s 涨到 140s**，而内核工作量**一模一样**（3,769,920 组合、5.7s）——
  多出来的时间全在"严格解为空 → 调谐补救"那条路上；
- 所以"属性不够极限"的真因是**没人要求过** + **要价太贵**，不是算法够不着。
  这决定了 P2（让用户能表达"顶"）与 P4（让"顶"别再花 140 秒）的分工。
