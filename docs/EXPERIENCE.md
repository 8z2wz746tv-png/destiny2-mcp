# 从这个项目里能带走的东西

**这份文档不是**使用说明（README 管那个），也不是决策台账（`docs/adr/` 管那个）。它是**经验提炼**：
destiny2-mcp 这个项目里，哪些架构与逻辑设计是**可迁移**的、为什么长成这样、哪些坑是用真机事故换来的。

两种读法：

- **你自己**：开新项目之前读一遍。重点是第二节（七条原则）、第三节（几个值得照抄的机制）和第六节（踩坑账本）。
- **你将来找的 agent**：把第七节整段贴给它当"项目宪法"。那比说十遍"写干净点"有用。

先说清规模，免得把个人项目的做法当行业标准：本地 Destiny 2 MCP 服务器，单进程、单用户，跑在自己机器上。
170 个模块 / 4.8 万行，112 个测试文件 / 1848 条测试（2026-09-28 实测收集 —— AGENTS.md 里记的 1652 是更早那次的数，
文档里的数字本来就会漂），21 条 ADR、16 份计划文档、299 次提交。全程是人 + agent 来回做出来的，没有团队。

## 一、整套架构其实只在解决一件事

如果只能记一句话，记这句。它来自项目里的一句 docstring：

> **宁可多拦一次，也不要留一个安静的错答案。**

为什么这句话能推出整套设计：这里的"用户"是语言模型。模型会猜、会顺着一句话往下编、会把
"我没查到"说成"没有"、会对着一个形状完整但答非所问的信封点头说"好的"。所以**接口的职责不是"尽量给点东西"，
而是让每一种"我答不了"都变成一个响亮的、机器可读的失败**。

同一个念头，在代码里长成这么多样子：

| 场景 | 不能这样 | 这个项目的做法 |
| --- | --- | --- |
| 参数传给了不读它的 intent | 静默丢掉，返回一整包别的东西 | 拒收，回 `ignored_parameter`，消息里点名"谁能读它" |
| 探测某件事时抛异常 | 记成"试过了，没有" | 记 `ok: null` + `not_probed` + `reason`（没探成 ≠ 试过没有） |
| 数据没读到 | 输出 0 / 空列表 | 给 `null`；"没查到"和"没有"是两个字段（`coverage_complete`、`unverifiable_reason`） |
| 写入成功但回读还是旧值 | 报成功，或报失败 | 报 `unverified` —— 上游确实回了成功，那是两件事 |
| 社区资料 | 和官方数据混在一张表里 | 带 `source_ref` + `trust=untrusted_reference`，与 Manifest/账号结果分块 |
| 上游故障 | 重试到成功、或包装成"参数错误" | 如实说是上游，说清是哪一类上游错误 |

这张表比任何"架构图"都更能说明这个项目在防什么。**如果你只从这带走一样东西，就带走它**：
先想清楚你的客户端会怎么把"答不了"伪装成"答了"，然后把每一处都焊死。

## 二、七条可迁移的原则

### 1. 一个事实只写一次，并且用测试禁止再抄

项目里每一类"会被抄第二遍"的事实，都有唯一的家：

| 事实 | 唯一的家 | 守门 |
| --- | --- | --- |
| 错误码 | `destiny_mcp/error_codes.py` | 扫描源码，禁止裸字符串；异常类名 ↔ 码 逐条钉住 |
| 中文词表（六维/职业/位置/元素/旧名） | `destiny_mcp/vocabulary.py` | 钉住官方名；旧名必须指向存在的规范名；禁止再抄一份 |
| intent 取值 / 写入 intent 清单 | `tools/_requests.py` | 与 skill 文档逐字核对 |
| 参数归属（谁读哪个参数） | `tools/_param_contracts.py` | 认领了必须真读、没认领必须拒收 |
| 响应信封 | `tools/_responses.py` | 语料 sweep 组对全部 intent 查信封规则 |
| 服务容器 | `service_context.py` | 架构层测试：`svc["…"]` 的 key 必须在这里声明过 |
| 组件号（上游魔法数字） | `services/profile_components.py` | 禁止裸组件字面量 |

**这不是审美，是两次真实事故换的：**

- 同一份"六维中文名"散在 9 个文件里，而且**值已经漂了**：官方是「生命值」，三处写成了「生命」，
  旧名映射还把玩家说的「韧性模组」换成「生命模组」——真机直接报"没找到护甲模组"。
- "这颗调谐能不能写"的判据被两条写入路径各写一份，只改了一边 → 3 颗本来能装的调谐被误拦，
  **连上游都没试**。修法不是改那一处，是把判据抽成 `build/tuning_writes.py` 两边共用。

**怎么找第二份拷贝**：问自己"同一个数据，能不能在两个文件里分别改得动？"能，就是第二份。

### 2. 口径写成可执行断言，不靠人记

项目里没有"请大家注意"这种句子，只有测试。三类守门：

- **禁止再抄型**：AST 扫描源码里有没有裸错误码字符串、有没有第二份异常→码的推导、有没有第二张词表。
- **契约钉住型**：手写一份"当前就是契约"的清单（错误码有哪些、异常类名映射到什么码），
  新增/改名会红，逼你**显式**决定。护甲模块的体量上限也是这个套路：数字就是当前长度，抬高要在 diff 里露出来。
- **行为断言型**：探测失败必须记 `ok: null`；写入类的 intent 不带确认必须不调用服务层。

配套纪律：**每个新守门都要先注入一次违规、确认它真的变红、再恢复**。不验证就不知道它会不会咬人 ——
一个永远不会红的测试，比没有测试更糟，因为它给了你安全感。

### 3. 不许静默降级，也不许替调用方下结论

四种写法，缺一不可：

1. **没算就不能说**：`analyze` 曾在没验证过的情况下断言"没有合法组合"，而同一组约束 `recommend` 能配出 100% 达标的方案。
   诊断类输出只说自己算过的东西。
2. **可选数据可以降级，但要带 `warnings`**：坏掉的可选资料不能弄坏主结果，也不能假装它没坏。
3. **结论路径的 `except` 必须留痕**：重抛、写进返回值、或者打日志。有一条测试专门扫这些模块的 `except`，
   吞掉失败却不留痕的直接红。
4. **缺值给 `None`，不编 `0`**：`null` 是"不在这个体系里/没这个数据"，不是零，也不是"丢了"。

### 4. 默认出口给"够判断的最小信息"，证明靠引用协议

这一条最容易吃亏，因为"多给点"看起来总是更友好。实测：

- 列出 1260 件背包物品 ≈ 511 KB ≈ 13–15 万 tokens —— 一次就把上下文烧掉一半。
- 配装列表从 121 KB 压到 2.8 KB 之后，用户的使用感受是"终于能看了"。
- 武器 perk 池压到 25 KB（原 45.4 KB），代价是**砍掉的必须是"列表类不需要"的字段**（描述、图标），
  而不是"反正用不上"的字段。

配套的做法是**引用协议**（ADR-021）：默认只给行 + 一个服务端签发的 `execution_id`，
要详情就带着这个 ID 再问一次（详情走确认信封）。这样"给少了"不会变成"给不了"。

### 5. 写入四步，一步都不许省

```
候选签发（服务端生成，带一次性 ID 与快照）
   → 用户明确确认（confirmed=true；没确认就不碰账号）
      → 执行
         → 回读核对（读到一致才算数）
```

三个细节是这个项目真正花时间的地方：

- **两道门槛**：一份 `WRITE_INTENTS` 集合列出所有会改账号状态的 intent（新增忘了加会红），
  加上 `confirmed=true` 的显式确认。确认信封里 `next_actions` 要写清"把 candidates[0] 里要改的东西说给玩家听"，
  否则模型会自己想下一步，而它想的那步经常是直接执行。
- **模型不能自己拼参数**：可执行的计划必须原样回传服务端签发的那份（或它的 ID）。
  用户自己拼 hash 会被挡住，并被告知"这不是服务端签发的候选配装"。
- **写入有同步窗口**：Bungie 的 profile 在写完 3～10 秒内回读可能还是旧值。写完立刻读一次会把**成功的写入报成失败**；
  但读不到也不能当成功。做法是重试一段时间（8 × 1.5 秒），仍读不到就说 `unverified`，并说清等过多久。
- **失败要说清停在哪一步、账号现在是什么状态**。"部分成功"报成功，是这个项目最不能接受的一类 bug。

### 6. 证据分档，谁也不能替代谁

三条不能破的线（原文进了给 agent 的技能文档和 MCP 握手说明）：

1. **账号数据**（我有什么）／**Manifest**（游戏里有什么）／**社区资料**（别人怎么说）互不替代；
2. 传给当前 `intent` 不读的字段会返回 `ignored_parameter`，按提示换入口，不要重试同一个调用；
3. 任何写入都要用户明确确认。

社区那档额外带两条：**保留出处与时间**（`source_ref`：url / updated_at / 快照哈希），
**保留不确定标记**（`[pvp]`、`[enh]`、`[unsure]`）。哈希只能证明"这份快照从哪来"，
不能证明"这些数字适用于当前版本"——这句写进了文档，也写进了响应的语义。

同一件事的另一面：**不许把"我们没做/我们做错了"说成"上游不允许"**。
项目里有一个 ADR 专门推翻自己（ADR-012 推翻 ADR-002）："护甲模组只能游戏内装"曾经是正式结论，真因却是**线上格式写错了**
（免费接口的字段名是 `itemId` 不是 `itemInstanceId`，以及 hash 要转无符号）。
归因错了，就会把一个纯 bug 记成"上游限制"，然后永远不再尝试。

### 7. 破坏性变更 > 兼容层；别名要么永久，要么登记待删

- 改响应形状时**旧键一个不留**（不双写、不留过渡分支、不保留"失败就退回旧路径"）。0.2.0 改活动统计形状时，
  8 个手写键直接消失。
- 别名分三类待遇，登记在 `docs/COMPATIBILITY.md`：**中文说法是永久别名**（删了等于砍功能）、
  **英文近义是待删别名**（登记不宣传，删之前先看真实调用日志）、**历史工具面整块归档**。
- 推翻旧决定时**不删旧 ADR**，把 `Status` 改成 `superseded by ADR-NNN`。理由很实在：
  漏一条的代价是下一个人把推翻过的决定又提一遍。

这套做法在个人项目里是划算的，因为它把"以后每次都要记得别用旧键"的成本，换成了"这一次改干净"的成本。
但它有账单，见第八节。

## 三、几个值得照抄的机制

### 3.1 三张契约表 + 一个信封

八个聚合工具各自只有一个宽签名，任何 intent 都能收到全部参数 —— 这是**故意的**：工具面对 agent 要小
（八个），但每个工具内部按 `intent` 分派。代价是必须有东西守住"哪个参数属于哪个 intent"：

- `_requests.py`：每个工具的 intent 取值（含中文别名）+ 写入 intent 清单；
- `_param_contracts.py`：参数归属表，判据是**行为上读没读**，不是"签名里有没有"。
  一个参数如果传了不改变任何结果，就算代码里被引用过，也不算认领；
- `_responses.py`：信封。

信封长这样，**成功和失败同一套骨架**：

```json
{ "ok": true,  "summary": "…", "data": {…}, "candidates": [], "next_actions": [], "warnings": [] }
{ "ok": false, "error": {"code": "…", "message": "…", "recoverable": true},
  "candidates": [], "next_actions": [], "warnings": [] }
```

失败时**详情永远在 `data.result`**。这条是收口收出来的：以前同一个"写不成"有三种读法
（通用写入放 `data.result`、`equip_build` 放 `candidates[0].result`、被挡住时放 `candidates[0]`），
调用方得按 intent 记三种找法——脚本里甚至留着一句"失败时 steps 在 candidates[0].result 里"的化石注释。

### 3.2 `ignored_parameter`：这个项目里最值钱的一个设计

```python
inventory_assistant(intent="get", item_instance_id="123")
```

没有这张表的时候，它会安静地丢掉 `item_instance_id`，然后像没事一样返回整包清单 ——
**信封完整、内容答非所问，调用方没有任何线索发现自己问错了入口**。

现在：拒收，消息里列出真正读这个参数的 intent，能给出替代入口的还带 `next_actions`。
三个**有意不登记**的参数也写进了 docstring（`confirmed`、`community_build_id`、`ctx`）：
不是遗漏，是决定 —— 文档里区分"我们没做"和"我们决定不做"，读者才敢信任其余部分。

### 3.3 三层配装类型：形状完整 ≠ 可执行

```
BuildRecipe（只是配方，全 hash）
  → CanonicalBuild（候选：实例 ID、逐件模组、快照版本、一次性 execution_id）
     → ExecutableBuild（可执行：五个部位齐全且互不相同、模组 hash 为正、快照与候选 ID 不为空）
```

（这条是 ADR-001，形状定义在 `destiny_mcp/build_contracts.py`。）

只有最后一层能执行，而且执行前还要再过一次服务端校验。

套到别的项目上就是一句话：**"看起来对"和"可以动手"，在类型上就是两个东西**。
把它做成两个类型，比在文档里写"注意别把模板当计划"有效得多。
（现实里已经有人踩过：社区配装模板结构统一，但**统一不代表验证过**，所以它永远不能直接执行。）

### 3.4 错误码：三个来源，类名即契约

- 工具层自己判定的失败 → `ErrorCode` 枚举里的字面量；
- 服务层抛异常 → 由异常**类名**推导（`InvalidArgumentError` → `invalid_argument_error`），
  一套正则只允许出现在一个文件里；
- 写入失败 → `write_failed(intent)`（`move_failed`、`equip_failed`…），按 intent 派生，不逐个进枚举。

有一条测试**禁止** `error_response("...")` 的第一参写字符串字面量。这条测试的来历是：以前 43 处直接写字面量，
打错一个字母不会报错，只会悄悄多出一个新码 —— 调用方按码判断就失灵，而且谁也说不清一共有多少种码。

### 3.5 停止线：决定"修不修"的规矩

写在测试语料文档里，是给人和 agent 一起用的：

- **P0/P1**（结果算错、数据丢、裸抛异常、账号有风险）→ 立刻修 + 出新版本 + 重跑回归；
- **P2/P3**（措辞、别名、文档不一致）→ 记进 backlog，**攒够一批再改**，不为一句话走一轮验证；
- 一轮回归发现 **0 条 P0/P1，即视为绿灯，可以停**。

最后那条最重要。没有停止线，"发现问题"这件事是无限的 —— 而无限的问题清单会让人彻底不想打开这个项目。

## 四、架构：分层与闸门

### 六层，只能向下依赖

```
0 纯基础      config / error_codes / exceptions / models / utils / vocabulary
1 基础设施    manifest* / bungie_client / bungie_errors / 实测事实表 / service_context
2 领域层      build/（配装求解，纯计算）  rag/
3 服务层      services/（账号读写、外部数据、形状工厂）
4 工具层      tools/（只做分派、参数守卫与话术）
5 装配层      server.py / __main__.py
```

守门测试做四件事：**新模块必须登记层号**（没登记就红，逼你决定它属于哪层）；
依赖只能向下；任何两个模块不许互相 import（跑一遍强连通分量）；
工具层用的每个服务 key 必须在 `ServiceContext` 里声明过。

为什么"忘了登记就红"比"在文档里提醒"有效：提醒会被跳过，红不会。
而且它把"分层"从一句口号变成了**每次加文件都要做的决定**。

### 体量闸：登记即上限

一份 `CEILINGS` 字典，每个"曾经或可能长成上帝模块"的文件都有一个当前长度当上限。规则：

- 超了 → 先抽代码，**不抬上限**；上限只能下调；
- 一份测试还检查"上限离实际不能太远"（余量 ≤ 40 行），否则这道闸就失效了；
- **拆出来的模块也要登记** —— 不登记等于给上限开后门：往新文件里堆代码时，老文件仍然"达标"，总量却在涨。
- **登记即上限**：加进去那一刻就是上限，等于说"下次再往这里加东西，先回答是搬出去还是抬上限"。

数字本身的说法很清醒：*"判断标准不是行数本身，而是新增代码该不该落在这个文件里。行数只是让这件事变成一次有意识的决定。"*

### 先钉行为，再拆结构

历史上有一次大拆分（manifest、武器载荷、装备编排都拆过）。拆的次序固定：
**先给这块行为写测试钉住 → 再动刀**。提交记录里能直接看到这个节奏（"pin the armor mod and subclass socket logic
before splitting it" → "split the loadout equipment service by domain"）。

反过来，"名字与依赖矛盾"是最早的信号：`utils/item_parser.py` 的 docstring 写着"no service logic"，
但它反向 import 了 `build.constants` / `manifest` / `services.armor_payload`。
**模块名说它是什么，不如它的依赖说它是什么** —— 它后来搬去了 `services/`。

## 五、和 agent 协作的方法论

这一节是"怎么让 agent 干出上面这些东西"，比代码本身更值得带走。

### 计划先行，但计划和决策分开放

- `docs/plans/*_PLAN.md`：**实机证据、取舍过程、阶段划分、落地记录**。一个功能一份，长期留着。
- `docs/adr/*.md`：只记**决定了什么和为什么**（连同被否掉的选项与代价）。

四种情况必须写 ADR：改对外契约、破坏性变更、推翻既有决定、**上游限制类结论**
（"不是我们选的，但会被反复问到"——写下来，免得每次重新试一遍）。

### 计划文档里最该学的一招：逐轮判决表

有一个真实需求：*"我要把某件金装穿上，花了 10 轮才成功。"* 复盘没有停在"下次注意"，
而是把 10 轮逐条判决成三类：**上游铁律**（游戏就是这样，我们只能编排，不能绕过）、
**我们的锅**（应该预检并直接说"先搬到角色身上"，而不是把 404 原样抛给调用方）、
**调用方的浪费**（agent 列了 103 件臂铠存文件再 grep —— 其实有一个 intent 是直接答这个问题的）。

这张表直接变成了实现方案（预检 → 出计划 → 确认 → 执行 → 回读核对）。
**遇到"用了很多轮才成功"，不要只修那一处，把每一轮判一个归属。** 归属决定方案：
上游铁律要"编排 + 说清"，我们的锅要"预检 + 好话术"，调用方的问题要"改入口/改提示"。

### 实测优先于文档

官方文档与真机结果冲突时，**以真机结果为准，并回头更新那一条实测记录**（ADR-003）。
推论：**外部快照不进仓库**（它是上游产物，不是我们的口径），需要离线深查时抓到仓库外，
带日期与指纹 ——"我们依赖的是自己的实测事实"。

### 提交：一行标题、一次只做一件事

提交信息只有一行，类型用中文（`修复` / `重构` / `文档` / `性能` / `语料` / `信封` / `词表` / `兼容面`…），
破坏性变更在标题里点明。细节全部在 CHANGELOG、计划文档和代码注释里，不写正文。
好处很直接：`git log` 本身变成一份可读的演进史，agent 接手时读几十行就知道发生过什么。

### 测试分层与预算（别把重活并发跑）

| 层 | 跑什么 | 什么时候跑 |
| --- | --- | --- |
| L1 自动化（不需要账号） | 单测 + 握手验证脚本 | 每次提交 |
| L1 自动化（需要账号） | 真机语料、基线 diff、性能基准 | 改动任一工具面后 |
| L2 冒烟（20 多行） | 真机逐条调用 | 每轮回归开始时 |
| L3 补测（其余行） | 真机逐条调用 | **只在该工具被改动时**跑它那一章 |

外加两条硬经验：**文档改动不要跑全量测试**（只动 `docs/**` 就跑那一个文档守门，5 秒）；
**别把重活并发跑** —— 实测并发时单测从 100 秒涨到 155 秒，还会让一条跟计时有关的测试假失败。

### 验收要打真链路

"注册成功"不等于"工具可用"。安装脚本跑完必须真的做一次 MCP 握手 + 一次只读调用，
并且检查工具数量与关键字段。同理，"装上 skill 了"不等于"agent 会按它做" ——
路由与参数归属由**契约测试**保证（文档里的表与代码逐字核对），行为由自然语言用例保证。

这条还有一个反向教训：**给 agent 看的文档也会烂**，所以它必须被测试守住。
项目的 `tests/test_skill_contracts.py` 拿代码去核对技能文档里的 intent 覆盖、参数归属、写入 intent 清单、社区分类。
文档红了说明**文档过期了**，不是检查太严。

## 六、踩坑账本

这些是真正花掉时间的坑，按"下次怎么避免"的顺序排：

| 现象 | 根因 | 教训 |
| --- | --- | --- |
| 43 处裸错误码字符串，谁也说不清一共几种码 | 没有唯一出处，打字错误静默生效 | 枚举 + AST 扫描；**新增一种码要显式过测试** |
| 真机报"没找到护甲模组 '韧性模组'" | 同一份中文词表 9 个副本，值已漂（生命 / 生命值） | 展示名唯一、输入别名多对一；旧名必须指向**存在**的规范名 |
| "个人应用没权限改模组，只能游戏内装"（正式结论，后来被推翻） | 归因错误：真因是免费接口字段名写错 + hash 有符号 | **写错的和上游禁止的必须分开说**；结论要留复现方式，好被推翻 |
| 3 颗能装的调谐被预检误拦，连上游都没试 | 同一条判据两条路径各写一份，只改了一边 | 判据抽出共用模块；两条路径的守门**成对**写 |
| `analyze` 断言"配不出来"，`recommend` 却能配出 100% 达标 | 没算完就下结论 | 诊断只说自己算过的东西；"没算完"要说成"没算完" |
| 探测抛异常被记成"试过、没有解" | `continue` + `for…else` 把失败吞成了否定结论 | **没探成 ≠ 试过没有**，要 `ok: null` + 原因 |
| 只请求插槽组件时上游一个插槽都不返回 | 读 305 必须同时带清单类组件（102/200/201/205） | 静默读空会**伪装成匹配逻辑错**；组件请求组合要有守门 |
| 写入成功后立刻回读，把成功的写入报成失败 | 上游有 3～10 秒同步窗口 | 回读要重试；仍读不到只能说 `unverified` |
| 同名多件护甲 → 回 `move_failed`，调用方重试同一个调用 | "需要你选一件"被报成了失败 | **没写 ≠ 失败**；给"需要选择"一个自己的错误码 |
| 每次修一处就长回来的上帝模块 | 没有闸 | 体量闸 + 登记即上限 + 上限只能降 |
| 文档里的 ADR 引用指向从未落盘的文件 | 编号从上一个项目带过来了 | 引用必须指向真实存在的文件，用测试扫 |
| `python -m x.server` 启动正常，但配装求解子进程必挂 | 子进程按路径重跑父进程主模块，模块方式重跑会 ImportError | **用法限制写进 README 并给唯一正确入口**，别只写"推荐" |

一条横向观察：**上半张表里一半的坑，表现形式都是"答得像真的"**（信封完整、字段齐全、话术通顺），
所以它们能活很久。这也是为什么第一节那句话值得当纲领。

## 七、给未来 agent 的开工规则（可直接粘贴）

下面这份是 domain-neutral 的骨架，来自这个项目 AGENTS.md 的浓缩。用的时候把 `<…>` 换掉，
把带 `※` 的条目换成你新项目的具体事实。

```markdown
# <项目名> 协作规则

## 先读什么
- README.md（怎么装、怎么验）→ AGENTS.md（本文件）→ <领域文档>
- 跑一次端到端验收脚本；"注册成功/装上了"不算证明。

## 三条不能破的线 ※
1. <数据分档>：<档 A> / <档 B> / <档 C> 互不替代；
2. 参数传给了当前分支不读的字段 → 报错并指出正确入口，不要静默忽略；
3. 任何改动外部状态的操作：先说清改什么 → 用户明确确认 → 执行 → 回读核对。

## 单一出处：一个事实只写一次
| 事实 | 唯一出处 | 守门测试 |
| --- | --- | --- |
| <错误码> | <文件> | 扫描禁止裸字符串 |
| <词表/枚举> | <文件> | 钉住取值，禁止再抄 |
| <对外响应形状> | <文件> | 对全部分支跑信封规则 |
新增共享事实时**先建表、再写守门**，不要复制第二份。

## 不许静默降级
- 没算完不说结论；没探到记 `unknown` + 原因，不记否定；
- 可选数据可以降级，但必须带 warnings，且不许弄坏主结果；
- 缺值给 `null`，不编 `0`；"没查到"和"没有"分开；
- 结论路径的 `except` 必须重抛、写进返回值或打日志。

## 破坏性变更
改对外形状时旧字段一个不留（不双写、不留过渡分支）；
别名要么是永久（用户的说法），要么登记待删（写进 <兼容面文档>）；
推翻旧决定时保留原记录、标 superseded，不删、不留空号。

## 分层与体量
新模块先在分层表登记层号，否则守门测试失败；
依赖只能向下、禁止环；
贴着上限的模块**只许抽代码**，抬上限要显式写在 diff 里。

## 提交与文档
提交一行标题、一次只做一件事；
跨主题的改动拆开；
计划文档记实测证据与取舍，决策记录只记"决定了什么和为什么"。

## 验证预算（<项目> 实测）
<pytest 全量 / 文档守门 / 端到端 / 真机语料 各多久、什么时候跑>;
不要并发跑重活；文档改动不跑全量。

## 停止线
P0/P1（算错、丢数据、裸抛、有风险）立刻修；
P2/P3（措辞、别名、文档不一致）攒批再改；
一轮回归 0 条 P0/P1 即绿灯，可以停。
不要主动巡逻式找 bug、不要每轮交一份"又发现 N 个问题"的清单。

## 密钥
永不进日志、提交、截图与聊天；只在本地配置文件里读。
```

## 八、账单：这套做法要付什么

不写代价的经验是假的。这套东西在个人项目里是划算的，但不是免费的：

- **时间**：全量单测按项目自己的记录约 2.5 分钟，真机全量语料 4–5 分钟，两者都不能跟别的重活并发。
  每个新守门还要走一遍"注入违规 → 确认变红 → 恢复"。
- **破坏性变更的成本**：每次改形状要同时动 代码 + 文档 + 语料 + 技能文档 + 兼容面登记。
  一次改动牵扯五处，这是选择了"不留兼容层"之后必然的代价。
- **文档量**：299 次提交里 67 次是纯文档，是占比最大的一类。一个人 + agent 的节奏下，
  这笔投入换来的是"三个月后还能读懂自己当初为什么这么定"。
- **什么时候不该学**：一次性脚本、原型、探索性验证。给它们配守门测试是负收益 ——
  闸门是给**会长期活着、会被人反复改的东西**配的。判断标准只有一个：这东西半年后还会不会改。
- **一条来自你自己的经验**：别让 agent 巡逻式找 bug。发现的问题要分"真的咬到人"和"一句措辞不好看"，
  后者最多一句话带过，不列待办。没有这条，上面所有规矩都会变成压力源。

## 九、术语速查（写给未来的你）

| 词 | 在这里指什么 |
| --- | --- |
| **intent** | 工具内的意图分派键。对外只暴露少量工具，每个工具按 intent 走不同分支 |
| **信封** | 响应的统一外层骨架（`ok` / `summary` / `data` / `candidates` / `next_actions` / `warnings`） |
| **守门测试** | 不是为了覆盖代码，而是为了**守住一条规矩**的测试（禁止再抄、契约钉住、行为断言） |
| **闸 / ratchet** | 只许收紧不许放宽的数值上限（体量、别名清单、错误码清单） |
| **登记即上限** | 把一个文件登记进体量闸那一刻，它的当前长度就成为上限 |
| **ADR** | 一条决定一份，只记"决定了什么和为什么"，与计划文档分工 |
| **实测优先** | 与官方文档冲突时以真机结果为准，并回头更新实测记录 |
| **停止线** | 决定"这轮修不修、什么时候可以停"的规矩（P0/P1 立刻修，0 条即绿灯） |
| **候选签发** | 服务端生成可执行计划并给它一个一次性 ID；调用方只能原样回传，不能自己拼 |
| **回读核对** | 写完之后再读一次确认；读不到（还在同步）叫 `unverified`，不叫失败 |
| **证据分档** | 官方定义 / 你的账号 / 社区参考，三类互不替代 |
